シミュレーションの実行 reference

このページは、ビルド済みの build/tenryu を前提に、「最初の 1 本を完走させる → 自分のデッキを書く → つまずいたら直す」までを通しで説明する。TENRYU の入力は、1 個の Python ファイルである。このファイルをデッキ（deck）と呼ぶ。TENRYU は、初期化の段階で、デッキの Python の関数を評価して表にし、設定を JSON（凍結設定、frozen configuration）に確定する。この操作を凍結（freeze）と呼ぶ。凍結のあと、時間ループの最中に Python が呼ばれることはない。凍結のほか、実効値（effective value）、limiter、床（floor）の意味は用語の節で説明する。

要点

  • 通常使う CLI サブコマンドは 4 つ: run（実行）・validate（実行せず検査）・verify（登録済み検証ケース）・freeze（凍結設定の JSON の出力）。run の前には必ず validate を実行する。設定ミスは実行前にほぼ全部見つかる。
  • 最初の 1 本は examples/templates/ のテンプレートをそのまま実行すればよい。編集せずに完走する。
  • tenryu とは常にビルドされた実行ファイル build/tenryu のことである — インストール手順はない。リポジトリのルートからパス指定で起動するか、build/ を PATH に加える。
  • スキーマは厳格である。未知のキー・型違い・不正な組合せは警告ではなくエラーで止まり、打ち間違いには did you mean 'kappa_a'? のような修正候補が出る。
  • 同じ出力先へ再実行すると上書きせず _001 の連番ディレクトリへ書かれる。「結果が変わらない」と思ったらまず出力先を確認する。

前提

マシン・コンパイラの条件は動作環境と要求スペック、build/tenryu の作り方はビルドを参照のこと。以下はビルドが済んでいて、リポジトリのルートにいる前提で書く。

CLI サブコマンド

コマンド入力用途
tenryu validate <deck.py>任意のデッキ実行せずに検査する（数秒）。スキーマ・組合せの検査に加え、次元・格子・材料・物理モジュールの ON/OFF・出力先をまとめた実行前の要約を表示する。run の前にこの要約を目で確認することが、最も安上がりなデバッグである。
tenryu run <deck.py>任意のデッキ本実行。デッキを読み、入力を検査し、凍結し、メッシュ・材料表・初期条件を作ってから時間ループに入る。--output-dir <dir> でデッキを編集せずに出力先を上書きできる（新規 run 専用。再開（restart）との併用は ConfigError）。再開では --t-end <s>・--max-steps <N> で終了時刻とステップ数の上限を延ばせる（run の延長）。
tenryu verify <name>登録済みケース名解析解・基準解・統合検査の再実行（例: sedov、noh、gxii_1d_fld_regression）。検証とベンチマーク参照。
tenryu freeze <deck.py>任意のデッキ凍結設定の JSON を書き出す。実行せずに実効値を確認し、デッキどうしで差分を比べたいときに使う。

最初の 1 本（テンプレートを完走させる）

examples/templates/ に、全ブロック（block）へコメントを付けた実行可能な雛形が 3 本ある。まずは一番軽い輻射スラブをそのまま動かす。

# ① 実行前検査（実行しない。数秒で終わる）
./build/tenryu validate examples/templates/template_1d_slab_radiation.py

# ② 実行
./build/tenryu run examples/templates/template_1d_slab_radiation.py

# ③ 結果の確認（出力先はデッキの Output(directory=...) が決める）
ls outputs/template_1d_slab_radiation/results/

③ で <name>_0000.h5 のようなスナップショットと <name>_history.h5 が並んでいれば完走である。実行中はコンソール（と、出力先 outputs/<name>/ 配下の log/）にステップの進行と、[output] wrote snapshot (step=…, …) のような出力イベントの行が流れる。最短の可視化は付属ツールで足りる:

python3 -m tools.tenryu_plot profile outputs/template_1d_slab_radiation   # 空間プロファイル
python3 -m tools.tenryu_plot history outputs/template_1d_slab_radiation   # 時系列
テンプレート内容学べること
template_1d_slab_radiation.py平面 1D・グレイ（gray）の流束制限拡散（flux-limited diffusion、FLD）・Marshak 境界駆動・流体 OFF輻射伝播の最小構成。validate → run → 可視化の流れ。
template_1d_laser_sphere.py球 1D・レーザー直接照射（direct drive）・2 温度（two-temperature）・熱伝導 ONレーザー波形の書き方、複合物理。
template_1d_indirect_tr.py球 1D・輻射温度 Tr(t) で外側の Marshak 境界を駆動する間接照射（indirect drive）時間に依存する関数（callable）を渡し、凍結で表にする書き方。

改造の定番は、駆動温度・レーザーパワー（callable の返り値）を変える、nr を倍にして収束を見る、Radiation(mode="sn_transport") にして FLD と比べる、の 3 つである。テンプレートはコピーして名前を変えてから改造する。物理指標まで確認済みの Studio プリセット 3 種は例題とプリセットにある。

デッキの構造

デッキは、ブロックと呼ぶ関数を呼んで設定を書く。ブロックは 11 個ある。Main はケース名、次元、終了条件を定め、Mesh は計算領域とセルの分割（zoning）を作る。Materials には、状態方程式（equation of state、EOS）と不透明度（opacity）をもつ材料を登録し、Geometry の関数が初期の体積分率、密度、温度、速度を空間へ割り当てる。Radiation と Laser は演算子を選び、Numerics は時間刻み、流体、熱伝導、ALE（arbitrary Lagrangian–Eulerian、任意ラグランジュ・オイラー法）と安全のための制御をまとめる。Output はファイルの場所と出力の間隔を、Diagnostics は実行中に集計する量を決める。Parallel は MPI（Message Passing Interface）による領域分割（domain decomposition）を、Burn は核燃焼（nuclear burn）を設定する。

次は、実在するキーだけで構成した最小の 1 次元球対称のデッキである。単一の理想気体の材料で一様に満たし、輻射・レーザー・熱伝導を無効にしてラグランジュ流体を進める。値は入力形式を説明するためのものであり、物理的なベンチマークではない。

from tenryu_namelist import *

fuel = Material(
    name="fuel", A=2.0, Z=1.0,
    eos=dict(model="ideal_gas", ideal_gas=dict(gamma=5.0 / 3.0)),
    opacity=dict(model="constant", kappa_a=0.0, kappa_s=0.0,
                 units="cm2_per_g"),
)

Main(name="minimal_1d", dimension="1D_SPH", temperature_model="2T",
     t_end=1.0e-9, max_steps=1000, seed=12345)
Mesh(r_min=0.0, r_max=0.05, nr=64, grid="uniform",
     motion="lagrangian")
Materials(materials=[fuel])
Geometry(
    volfrac=dict(fuel=lambda r_cm: 1.0),
    rho=lambda r_cm: 1.0,
    Te=lambda r_cm: 1.0,
    Ti=lambda r_cm: 1.0,
    velocity=None,
    radiation_field="zero",
)
Radiation(enabled=False)
Laser(enabled=False)
Numerics(
    dt=dict(initial_s=1.0e-12, max_s=1.0e-10, min_s=1.0e-18,
            cfl_hydro=0.3),
    hydro=dict(boundary_1d="free"),
    conduction=dict(enabled=False),
)
Output(directory="outputs/minimal_1d", plot_every=10,
       history_every=1, checkpoint_every=100)
Diagnostics(enabled=True, every=1)

自分のデッキを書くときの原則

  • 単位は常に cgs + eV。長さ cm・時間 s・密度 g/cm³・温度 eV。µm で書きたいときは um = 1.0e-4 を自分で定義して換算する。名前が単位を明示するキー（wavelength_nm など）だけが例外である。
  • 空間分布と時間波形は関数で与える。Geometry.rho・Te・Ti・volfrac はセル中心の座標を、レーザーパワーや Marshak 温度は時刻を、スカラー（float）で 1 つずつ渡して初期化時に評価し、凍結された表へ変換する。関数は数値を受け取って数値を返せばよい。NumPy の関数は使えるが、スカラーの引数で動かなければならない。関数が外部状態を持ち続けることや、実行中に再評価されることを前提にしたデッキは正しくない。
  • 書かなかったキーは既定値になる。既定値の正典はリポジトリの docs/SPECIFICATION.md §9.1。迷ったら書かず、validate の要約と出力先の config/*_frozen.json で実効値を確認するのが安全である。
  • 打ち間違いはエラーで止まる。未知のブロックやキー、文字列を要求する場所への数値、負のセル数、選んだ次元では対応していない組合せは、黙って無視されず ConfigError になる。修正候補（did you mean …?）が出たらそのまま直す。
  • 物理は 1 個ずつ足す。交差ビームエネルギー転送（cross-beam energy transfer、CBET）、ホット電子（hot electron）、Schurtz–Nicolaï–Busquet モデル（SNB）による非局所熱伝導、プラズマ粘性（plasma viscosity）、核燃焼は、デッキに有効化のキーを書いたときだけ働く。既定では無効である（有効化のキーは次元と有効化の早見表にある）。新しいデッキは、まず小さいメッシュと短い t_end で初期化と数ステップを確認し、そのあとで実運用の解像度と出力の間隔へ上げること。

この計算で使う用語

このページで、TENRYU の実行に固有の意味で使う語は、凍結、実効値、limiter、床の 4 つである。デッキ、ブロック、キーはnamelist のページで定義する。

凍結

凍結（freeze）は、デッキの内容を、時間ループに入る前に、ループの中で変わらない形に確定する操作である。このページでは、次の 2 つの意味で使う。

  • 関数の評価と表への置き換え。デッキの Python の関数（callable）を、格子と時間軸の上で評価して、数値の表に置き換える。空間分布の関数 Geometry.rho・Te・Ti・volfrac は、既定では、各セルの中心（2D では重心）の座標をスカラー（float）で 1 つずつ渡して評価し、セルごとの初期値にする。Geometry.velocity は、節点の座標で評価する。時間の関数（LaserBeam.power、Radiation.boundary.marshak_Tr と面ごとの marshak_Tr_map、Numerics.hydro.boundary_pressure、Laser.hot_electron.eta_hot_table と生成源ごとの eta_table）は、時刻をスカラーで 1 つずつ渡して評価し、区分線形の表にする。表の時刻は、0 から Main.t_end までを \(2^{-40}\) s（約 \(9.1\times10^{-13}\) s）ごとに取る。区間の中点での関数の値が、両端の値の平均から、3 点の値の絶対値の最大値の \(10^{-6}\) 倍を超えて離れているときは、その区間を二分して点を足す（\(2^{-47}\) s の刻みまで）。Main.t_end が約 0.95 µs を超える run では、区間の数が \(2^{20}\) 以下になるまで、基本の刻みを 2 倍ずつ粗くする。時間ループの中では、この表を線形補間して使う。
  • 設定の JSON への確定。デッキの実行が終わると、各ブロックのキーを検査し、書かなかったキーに既定値を補って、設定の全体を 1 個の JSON（凍結設定）にする。関数は、値ではなく、関数の名前、repr（文字列表現）、ソースコードの SHA-256 ハッシュ（source_hash）で JSON に記録する。デッキ本文の SHA-256 ハッシュ（_namelist_source_hash）も入る。

凍結する理由は 2 つある。第一に、時間ループの中で Python を呼ばないためである。TENRYU は、組み込みの Python インタプリタを、デッキの実行と凍結のためだけに起動し、時間ループに入る前に終了する。ステップごとに Python の関数を呼ぶ設計は、速度と再現性を損なうので、仕様が禁じている（リポジトリの docs/SPECIFICATION.md §6.3.1）。第二に、再開のときに、設定が元の run と同じであることを照合するためである。

凍結は、次の 3 つに効く。

  • 凍結設定のファイル。tenryu run は、凍結設定を出力先の config/<name>_frozen.json に書く（Output.save_frozen_config、既定 True）。デッキのコピーも config/<name>_namelist.py に置く（Output.save_namelist_copy、既定 True）。ファイルには、実行時の上書き（--output-dir、再開時の --t-end・--max-steps）を反映した値が入り、凍結した時刻（_frozen_at）、TENRYU の版（_tenryu_version）、評価した表の要約（frozen_summary）が加わる。要約には、初期の密度の最小値・最大値・平均値、電子温度とイオン温度の最小値と最大値、材料ごとの体積、時間の表の範囲・点数・最大値・積分値が入る。run の来歴の一次資料として使う（出力と解析）。
  • tenryu freeze。デッキを実行して、凍結設定だけを書き出す。メッシュと初期状態を作らず、表も作らないので、frozen_summary は入らず、実行時の上書きもない。出力先は -o <file> で指定し、省略するとカレントディレクトリの <デッキのファイル名（拡張子なし）>_frozen.json に書く。デッキのコピーも、出力ファイルと同じディレクトリに置く（すでにそこにあるときを除く）。
  • 再開時の照合。チェックポイントは、凍結設定を metadata/frozen_config に、デッキ本文を metadata/namelist_source に保存する。再開では、この凍結設定と、再開に使うデッキから作った凍結設定を、Main.restart_from を除いて比べる（古いチェックポイントに無いキーには、既定値を補ってから比べる）。1 か所でも違えば、時間ループに入る前に停止する。デッキ本文が 1 文字でも違えば _namelist_source_hash が変わるので、再開は拒否される。拒否のメッセージ（checkpoint frozen_config JSON mismatch）は、違いのあるキーを differs at: に最大 8 個示す（チェックポイントと再開）。照合に使う凍結設定は、実行時の上書きの前の値から作り、凍結の時刻・版・表の要約を含まない。そのため、--output-dir や --t-end で上書きして走らせた run のチェックポイントも、元のデッキを変えずに再開できる。

実効値

実効値（effective value）は、デッキに書いた値に、書かなかったキーの既定値を補い、実行時の上書き（--output-dir、再開時の --t-end・--max-steps）を反映した、実行が実際に使う値である。二乗平均平方根（root mean square、RMS）の意味ではない。デッキに書いた値だけでは、既定値の補完や上書きのために、実行が何を使ったかが分からない。設定が効いたか疑わしいときは、実効値を先に確かめる（うまくいかないとき）。run が使った実効値は、出力先の config/<name>_frozen.json にある。run の前に確かめるには、tenryu freeze の出力を読む（実行時の上書きは入らない）。tenryu validate の要約は、実効値の主な項目を人間が読める形で示す。デッキに書いた値と実効値が違う例に、温度の床がある。デッキに温度の床（Numerics.floors.Te_floor_eV・Ti_floor_eV）を書かず、テーブル EOS の最低温度が既定の床 \(10^{-3}\) eV より高いときは、床がその最低温度に引き上げられ、凍結設定には引き上げた値が入る（リポジトリの docs/NUMERICS.md §1.1.5）。

limiter

limiterは、そのステップの時間刻み \(\Delta t\) を決めた制約の名前である。\(\Delta t\) は、各物理カーネルが提案する上限と、成長率の制限、Numerics.dt.max_s、出力時刻への着地、残り時間のうち最小のものに等しく、勝った候補の名前（hydro・conduction・braginskii・burn・hot_electron・growth・max・output・t_end など）が limiter になる。Main.verbosity="verbose" で実行すると、ログの [dt_breakdown] 行の dt_winner= に毎ステップ出る。履歴にも dt_winner として残る。\(\Delta t\) が縮み続けて進まないときは、limiter が原因のカーネルを示す（実行中に見えるもの）。名前の一覧と決定則は時間刻み制御と CFLにある。流束制限拡散の流束制限関数（flux limiter）や、ALE のリマップの勾配制限（remap_limiter）は、別のものである。

床

床（floor）は、密度と温度の下限値である。計算の途中で値が下限を割ると、下限まで引き上げ（クランプ、clamp）、引き上げに要したエネルギーをエネルギー台帳（energy ledger）に記帳する。床は物理モデルではなく、NaN や負の温度で計算が壊れるのを防ぐ数値上の安全装置で、発動はすべて数えられる（床・クランプ・安全ガード）。キーは Numerics.floors の rho_floor_gcc（既定 \(10^{-10}\) g/cm³）、Te_floor_eV・Ti_floor_eV（既定 \(10^{-3}\) eV）で、Studio も同じ値を書き出す。床は、時間刻みの下限 Numerics.dt.min_s とは別のものである。\(\Delta t\) がこの下限を割ると、run は FATAL で停止する（デッキで指定しないときの既定は \(10^{-20}\) s、Studio が書き出す値は \(10^{-22}\) s）。

実行中に見えるもの

run は最初にデッキを検査し（validate と同じ検査）、凍結して、メッシュと初期状態を構築してから時間ループへ入る。以後はステップの進行がログに流れ、スナップショットを書くたびに [output] wrote snapshot (step=…, …)、チェックポイントを書くたびに [output] wrote checkpoint (step=…, …) の行が出る。ログはコンソールと outputs/<name>/log/ の双方に残る。

「\(\Delta t\) がどんどん小さくなって進まない」ときは、ログの limiter 名（hydro・conduction・braginskii など）で律速カーネルを特定し、該当物理の設定（床・格子）を見直す。決定則と全カーネルの式は時間刻み制御と CFL にまとめてある。

出力先

スナップショット、履歴、チェックポイントは Output.directory に書き出される。ケース名に合わせた outputs/<name> が標準的な整理の仕方である。ディレクトリの内訳（results/・config/・checkpoints/・log/・run_info.json）、ファイルの命名、データセットの一覧は出力と解析にまとめた。plot_every・history_every・checkpoint_every はステップ数で指定する間隔（0 で無効）、_s 付き（plot_every_s 等）は秒で指定する間隔で、両方が有効なら OR で発火する。時間で指定したいときは必ず _s 付きのキーを使う。ステップ数と秒を取り違える単位の誤りは起きやすい。

チェックポイントと再開

再開は、元の run と同じデッキファイルを内容を変えずに使い、チェックポイントの接頭辞（ランクの接尾辞や .h5 を除いたもの）を --restart で渡す。たとえば ./build/tenryu run minimal_1d.py --restart outputs/minimal_1d/checkpoints/minimal_1d_ckpt_0000 とする。再開の照合は、チェックポイントの凍結設定と、再開に使うデッキから作った凍結設定を、デッキ本文のハッシュと、Main.restart_from を除くすべての設定について比べる（凍結）。一致しなければ開始する前に失敗する（checkpoint frozen_config JSON mismatch）。デッキに restart_from を書き足す、t_end を延ばす、出力の間隔を変える、コメントを足すなど、本文を少しでも変えると再開できない。接頭辞をデッキに持たせたいときは、元の run のデッキから restart_from=os.environ.get("RESTART_FROM", "") のように環境変数から読み、本文を変えずに渡す。一致するチェックポイントがない場合も開始する前に失敗する。再開は、チェックポイントに保存された状態、時刻、時間刻み、次の出力時刻を引き継ぐ。出力はデッキの Output.directory に書き、そのディレクトリが既にあれば _001 などの通し番号を付けた新しいディレクトリに書く。1D の run は、2026-09-26 以降に書いた途中のチェックポイントから再開すると、元の run とビット一致（bitwise identical）で続く。GXII（激光 XII 号、GEKKO XII）の FLD・離散座標法（discrete ordinates、SN）のデッキと、核燃焼を含むデッキで、履歴の全列が一致することを確かめている。ただし、前回の光線追跡（ray tracing）の結果をパワーの比で再スケールして再利用する設定（Laser.raytrace_skip_config.enabled=True、既定は False）の run は、再開直後に全光線を追跡し直すので一致しない。2026-09-25 より前の 1D の SN の run を再開するときは、Radiation.sn_transport.spatial_scheme="linear_characteristic" を明示すると従来の空間離散化で続く。

run の延長

終えた run を、終了時刻やステップ数の上限を延ばして続けるには、デッキは変えずに新しい値を CLI で渡す：./build/tenryu run <deck.py> --restart <checkpoint> --t-end <s>（または --max-steps <N>）。終えた run の最後から続けるには、元の run のデッキに Output(..., write_final_checkpoint=True) を入れておき、終了したステップのチェックポイントを残す。途中のチェックポイントからも同じ方法で延ばせて、デッキの t_end より前から延ばした run は、延ばした値をデッキに書いて最初から走らせた run とビット一致する（1D の FLD で確認）。延ばした値はチェックポイントの凍結設定に入らない（デッキの値のまま）ので、延ばした run のチェックポイントから、同じデッキと新しい値でさらに続けられる。実際に使った値は run_info.json の t_end・max_steps に記録する。--t-end・--max-steps は再開専用で、チェックポイントがすでに終了時刻やステップ数の上限に達しているのにこれらを渡さないと、どちらを渡せばよいかを示して開始前に止まる。LaserBeam.energy_J の正規化はデッキの t_end までの区間のままで、パルスがその後も続くと延ばした区間の分だけエネルギーが追加で入る（WARNING に量が出る）。延ばした run の出力はデッキの Output.directory の隣の _001 などに書かれる。途中のチェックポイントから続けた場合、続きは元の出力の終わりの区間を計算し直すので、Studio の履歴のグラフと TENRYU Scope（スナップショットの一覧と時空図）は、その区間を続きの結果で表示する。

うまくいかないとき

入力の誤りは、例外 ConfigError または ValueError（検証と既定値）として報告され、先頭が TENRYU ERROR [namelist]: の行で表示されて、終了コード 1 で止まる。デッキの実行中に見つかった誤りは、Python execution failed: RuntimeError: に原因の文が続き、At: の次の行にデッキの行が示される。出力の準備や時間ループの中で、それ以外の例外が出て止まるときは、先頭が TENRYU ERROR [run]: の行になる。表明（assertion）の失敗は、TENRYU_ASSERT failed: に条件と原因の文が続く行を出して、異常終了する。
