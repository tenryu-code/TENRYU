ビルド reference

TENRYU は C++20 / CUDA C++ のコードを CMake と Ninja で構成し、CUDA 12.x のツールキットと NVIDIA GPU(既定 fatbin は sm_70/80/89/90、継続検証している実機は sm_80 以降)を対象にビルドする。このページでは、リリースビルドの作成、全体・対象限定・名前指定の 3 段階のテスト、MPI の有効化、そして ccache を使った反復ビルドまでを扱う。

要点

  • 必要なものは、CUDA 12.x のツールキット、CMake 3.25 以上、Ninja、そして NVIDIA GPU(検証済み実機は sm_80 以降)である。
  • 標準の手順は、cmake で build/ を構成し、ninja -C build でコンパイルする 2 段階である。
  • 確認は、CTest の全実行、-R による対象限定の CTest、tenryu verify による名前指定の検証を、目的に応じて使い分ける。
  • MPI は既定でオフである。複数ランク用のバイナリを作るには、構成時に -DTENRYU_ENABLE_MPI=ON を指定する。

前提条件

ビルドは NVIDIA CUDA の環境上で行う。CUDA のコンパイラとドライバが見えていることに加え、CMake が CUDA のツールチェーンと依存ライブラリを検出できる必要がある。HDF5 と Python への対応は最上位の CMake で既定オン、MPI は既定オフである。追加機能の有無を変える場合も、まずは同じ「構成 → ビルド」の流れを保つこと。要求の全体像（対応 GPU 世代・コンパイラ・全ライブラリの最低バージョン・CMake オプション一覧・事前チェックのコマンド）は動作環境と要求スペックにまとめてある。以下は要点の再掲である。

ネットワークについて。テスト・ログ・CLI 系の小依存（Catch2・spdlog・CLI11・pybind11）は、システムに見つからない場合 CMake の FetchContent が構成時に自動取得する。オフライン環境では事前導入するか、ネットワークのある場所で初回の構成を済ませること。CUDA・HDF5・Python・MPI・Hypre は自動取得の対象外である。

項目要件役割
GPUNVIDIA 製。既定 fatbin は sm_70;80;89;90、検証済み実機は sm_80 以降。CUDA カーネルと検証の実行先である。
CUDA ツールキット12.x (12.0 以上)nvcc、CUDA のヘッダ、実行時ライブラリを提供する。
CMake3.25 以上C++20 / CUDA のターゲット、依存関係、CTest を構成する。
Ninja利用できること生成されたビルドの依存グラフを並列に実行する。
HDF51.12 以上 (既定でオン)スナップショット・履歴・チェックポイントの入出力を担う。MPI の集団出力には並列 HDF5 を使う。
Python + pybind11Python 3.10 以上、pybind11 2.11 以上 (既定でオン)初期化時にだけ namelist を読む組み込みインタープリタである。
任意の機能MPI 3.1 以上 (-DTENRYU_ENABLE_MPI=ON)、Hypre — LLNL の線形ソルバライブラリで、その BoomerAMG 前処理が熱伝導の任意の solver="hypre" 経路を支える有効にした CMake のオプションに対応する開発用パッケージが必要である。

ソースコードの入手

ソースコードは GitHub リポジトリ tenryu-code/TENRYU から取得する。以降の手順はすべて、clone したリポジトリのルートで実行する。

git clone https://github.com/tenryu-code/TENRYU.git
cd TENRYU

特定のリリースを使う場合はタグを checkout する（例: git checkout v1.0.0-beta.1）。既存の checkout を更新するには git pull を実行してから、あらためてビルドする。

構成とビルド

リポジトリのルートで次の 2 つのコマンドを実行する。最初のコマンドはソースツリーを変更せず、リリース用のビルドツリーを build/ に生成する。2 つ目は既定のターゲットをコンパイルし、build/tenryu と、有効になっているテストのターゲットを作る。

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
ninja -C build

ソースやビルド設定を変更したあとの差分ビルドは、通常 ninja -C build を実行し直せば十分である。CMake のオプションを変える場合は、構成のコマンドを新しいオプション付きで実行し直してから Ninja を走らせる。CMake の診断でパッケージが見つからないと出た場合は、そのパッケージを導入したうえで、同じ構成コマンドを実行し直すこと。

ビルドが通ったら、時間ループまで含めた最小の動作確認として、登録済みの解析解ケースを 1 本走らせる。

./build/tenryu --help          # CLI が起動すること
./build/tenryu verify noh      # 解析解ケースが PASS すること（GPU を使う）

ここまで通れば、シミュレーションの実行のテンプレート完走へ進める。

テストの 3 段階

すべての確認を、常に同じ粒度で走らせる必要はない。CTest の全実行はビルド全体の健全性を、対象を限定した CTest は変更したモジュールの周辺を、名前を指定した検証はひとつの物理問題や回帰を直接確認する。失敗したときに出力を残すため、CTest の全実行では --output-on-failure を付ける。

ctest --test-dir build -j8 --output-on-failure
ctest --test-dir build -R <pattern>
./build/tenryu verify <name>
段階使いどころ選び方
CTest の全実行統合の前や、広い範囲を変更したあとの回帰確認。ビルドツリーに登録されたすべてのテストを 8 並列で実行する。
対象を限定した CTest開発中の短い反復。<pattern> をテスト名の正規表現に置き換える。たとえばモジュール名や検証名を使う。
名前を指定した検証特定の解析解、ベンチマーク、基準解との回帰。<name> を sedov や gxii_1d_fld_regression などに置き換える。

-R は部分一致なので、意図より広いテストの集合を選んでしまう可能性がある。実行対象を先に確かめたいときは CTest の一覧表示(ctest --test-dir build -N -R <pattern>)を使い、ログではスキップと合格を区別すること。GPU や任意の依存関係がないために実行されなかったテストは、合格したテストの代わりにはならない。

MPI 対応のビルド

複数ランクでの実行用には、同じリリース構成に MPI のオプションを追加する。MPI の実装とヘッダが CMake から見える環境で実行すること。

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DTENRYU_ENABLE_MPI=ON
ninja -C build

TENRYU_ENABLE_MPI は最上位の CMake のオプションで、既定値は OFF である。すでに構成済みの build/ に対してオプションを切り替えた場合も、CMake の再構成のあとに Ninja が必要なターゲットを再ビルドする。MPI 対応バイナリの実行方法と、ランクごとの GPU の割り当てについては、MPI 分割のページを参照のこと。

ccache による反復ビルド

ヘッダを含む再コンパイルを繰り返す環境では、ccache をコンパイラのラッパとして使うと、既にコンパイル済みのオブジェクトを再利用できる。ccache が PATH にある状態で、構成のコマンドに次の 2 つを追加する。

-DCMAKE_CXX_COMPILER_LAUNCHER=ccache \
-DCMAKE_CUDA_COMPILER_LAUNCHER=ccache

C++ と CUDA の両方を指定することが重要である。ccache はコンパイルの時間を短くするが、構成、リンク、テストを省く仕組みではない。ツールチェーン、コンパイルオプション、ヘッダが変わればキャッシュのキーも変わり、必要なコンパイルは通常どおり実行される。
