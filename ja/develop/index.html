開発者ガイド reference

TENRYU への変更は、物理モデル、入力の仕様、実装、検証（verification）、文書がひとつの追跡可能な変更としてまとまるように構成する。内部の単位系を cgs + eV に固定すること、namelist のキーを厳格に検査すること、既存の検証の試験を壊さないこと、同じ構成の実行が毎回同じ結果を返すこと、初期化のあとは Python を呼ばないことは、性能や利便性のために後回しにしてよい事項ではなく、すべての変更が守る条件である。

要点

  • 内部の単位系は cgs + eV に固定されている。内部を SI 化したり別の単位系へ置き換えたりする変更は受け入れない。
  • 未知の namelist のキーはエラーとし、すべてのキーについて型、単位、制約、既定値を文書化する。
  • 数式と離散化の変更は NUMERICS.md を、新しいキーは SPECIFICATION.md を、同じ変更のなかで更新する。
  • 決定論的（deterministic）な 1D の経路と 2D RZ の経路は、同じ構成の反復実行でビット単位の一致（bitwise identity）を要求する。粒子の乱数は global_id ごとに独立した系列にする。

リポジトリの構成

主要な実装は src/ にあり、core が状態・設定・単位、mesh が幾何とメッシュの接続関係（mesh topology）、hydro がラグランジュ流体（Lagrangian hydrodynamics）と ALE（arbitrary Lagrangian–Eulerian、任意ラグランジュ・オイラー法）、radiation が FLD（flux-limited diffusion、流束制限拡散）/ SN（discrete ordinates、離散座標法）、laser が光線追跡（ray tracing）と沈着（deposition）、materials が EOS（equation of state、状態方程式）と不透明度、coupling が演算子の時間発展、diagnostics が履歴と物理指標、drivers がコマンドの入口を担当する。tests/ は単体試験と統合試験、examples/ は利用例と検証用のデッキ（deck）、docs/ は設計・仕様・数値手法の文書、gui/ は TENRYU Studio を収めている。変更する前に、担当するモジュールと、影響を受ける試験・例・文書を特定すること。

単位系と namelist の仕様

TENRYU の内部表現と入出力は cgs + eV である。長さ cm、時間 s、質量 g、エネルギー erg、密度 g/cm³、温度 eV という既存の取り決めを維持し、内部の状態を SI などへ変えることはしない。人が読み書きしやすい入力として別の単位を受け付ける場合も、境界で明示的に変換し、物理カーネルと状態がもつ単位、定数、式の係数を曖昧にしない実装が必要である。単位の変換を伴う変更は、数式、パーサ、凍結（freeze）した設定、入出力、検証の参照値を一体として扱う。

namelist のスキーマ（schema）は厳格である。未知のブロックやキー、打ち間違い、型の違い、範囲外の値、対応していないモードの組合せは、無視や警告ではなく入力エラーにする。新しいキーには、完全修飾名、型、単位、許容範囲、相互の制約、既定値を定義すること。明示的な値を書かないデッキの挙動も公開している入力の仕様の一部なので、既定値は実装のなかに隠さず、正典となる仕様に記載する。後方互換のための別名（alias）が必要な場合も、優先順位と、競合したときのエラーを明示し、黙ってどちらかを選ぶことのないようにすること。

文書と実装を同時に変更する

このページが参照する設計文書 — docs/NUMERICS.md、docs/ARCHITECTURE.md、docs/SPECIFICATION.md — は、TENRYU リポジトリにコードと並んで置かれ、ソースとともに公開されている文書である。数式、物理の係数、時間積分、空間の離散化、境界条件、単位の規約を変更する場合は、同じ変更のなかで docs/NUMERICS.md を更新する。NUMERICS.md は、実装から推測するための解説ではなく、式と離散化についての正典（実装が従う基準の文書）である。モジュールの責務やデータの流れが変わる場合は、docs/ARCHITECTURE.md も更新する。

新しい namelist のキーを追加する場合は、docs/SPECIFICATION.md §6.4 の該当スキーマと、§9.1 の既定値の一覧を、同じプルリクエスト（pull request）で更新する。利用者向けのページや例に影響するなら、それらも合わせて変更すること。コード、既定値、凍結した設定、検証、文書のうち、どれかだけが先行した状態では、公開している入力の仕様を再現できない。

検証と基準解

変更によって examples/verification/ の関連する検査を壊してはならない。局所的な物理カーネルの試験だけでなく、変更した演算子が通る解析解（analytic solution）のケース、保存則、連成した回帰を選び、意図しない差がないことを確認する。検査の種類と判定基準は検証とベンチマークの頁にある。失敗を、許容差の拡大や期待値の移動だけで消すのは修正ではない。原因を符号、単位、境界、係数、離散化、参照値のどこに求めるのかを明確にすること。

基準解（golden。承認した実行の指標値を保存した参照値で、定義は検証の頁の凡例にある）は、tenryu verify gxii_1d_fld_regression --generate-golden で取り直す。基準解の更新には、明示的な正当化が必要である。既知の不具合の修正、レビュー済みの物理・数値アルゴリズムの変更、基準となるパラメータの意図的な変更などを示し、旧値と新値の差、影響する指標、必要な収束の確認または独立な参照を記録する。単に現在の出力へ基準解を合わせることは認められない。既存の検査が確認していない新しい挙動には、新しい正解の基準または診断を追加する。

再現性の要求

決定論的な 1 次元の実運用の経路では、同じバイナリ、入力、GPU 構成のもとで、場と主要な診断量が実行のたびにビット単位で一致することを要求する。物理的な許容差をもつ回帰試験であっても、それが同じ構成での反復実行のずれを許す理由にはならない。2D RZ でも、1 ステップ内の浮動小数点の和は固定順に置き換えてあり、同じ構成の 2 本の実行は、状態、時間刻み、エネルギー台帳（energy ledger）、診断のすべてがビット単位で一致しなければならない。加算順序に依る atomicAdd（原子加算）を足す変更は、固定順の和にするか、順序に依らない理由を tools/checks/atomic_add_allowlist.json に記録しなければならない（ctest -R atomic_add_allowlist が、一覧にない呼び出しを落とす）。反復実行の差を許す帯（雑音帯、noise band）を使うのは、固定順にできない和が残る経路に限り、デッキと指標ごとに文書化した帯の範囲だけとし、一般的な許容差として広げることはしない（帯の定義は検証の頁）。

確率的（stochastic）な粒子の経路における乱数の系列は、粒子ごとの global_id と種、ステップによって独立に識別される。生成、複製、移送、再開（restart）の変更によって ID の空間を衝突させたり、並列の領域分割によって同じ粒子の系列を変えたりしてはいけない。乱数の分割は、保存形式や MPI を含む再現性の要求に関わるので、局所的な最適化として変更しないこと。

Python は初期化時に凍結する

Python の namelist における関数は、読みやすい初期条件や時間波形を書くための入力の仕組みである。関数は初期化（initialization）の段階でメッシュまたは時間軸の上で評価して表へ変換し、凍結した設定（frozen configuration）と、C++ / CUDA 側が所有するデータへ移す。時間ループや CUDA カーネルから Python を呼び出す実装は追加しない。この境界によって、実行時の依存、GIL（global interpreter lock、Python のグローバルインタプリタロック）、外部状態の変化、ランクごとの評価の差を、計算から取り除ける。新しく関数を受け取る入力を追加する場合も、評価する定義域、表の解像度、ハッシュと凍結した設定の表現を定義すること。

プルリクエストの範囲

ひとつのプルリクエストは、ひとつの目的に限定する。不具合の修正、物理モデル、性能の調整、リファクタリング、スキーマの移行を無関係に混ぜると、数値の差の原因と検証の証拠を切り分けられない。とくに、物理の変更と性能の変更は同じプルリクエストに入れず、まず物理の仕様と基準となる出力を確立し、そのうえで結果を変えない最適化として提出すること。説明には、目的、変更した仕様と判定基準、影響の範囲、実行した検査、検証していない構成を記載し、レビュアーが差分と証拠を一対一で追える状態にする。外部からの貢献は、まず GitHub の Issues で変更内容を相談してから着手すること（ライセンス上、変更版の公開・再配布には書面許可が要る）。
