開発者ガイド reference

TENRYU への変更は、物理モデル、入力の契約、実装、検証、文書がひとつの追跡可能な変更としてまとまるように構成する。固定された cgs + eV の単位系、厳格な namelist、検証の関門、再現性、初期化のあとは Python を呼ばないという実行時の境界は、性能や利便性のために後回しにしてよい事項ではなく、コードベースが公開している契約である。

要点

  • 内部の単位系は cgs + eV に固定されている。内部を SI 化したり別の単位系へ置き換えたりする変更は受け入れない。
  • 未知の namelist のキーはエラーとし、すべてのキーについて型、単位、制約、既定値を文書化する。
  • 数式と離散化の変更は NUMERICS.md を、新しいキーは SPECIFICATION.md を、同じ変更のなかで更新する。
  • 決定論的な 1D の経路はビット単位の一致、2D の例外は文書化した雑音帯、粒子の乱数は global_id ごとに独立した系列、というのが契約である。

リポジトリの構成

主要な実装は src/ にあり、core が状態・設定・単位、mesh が幾何と接続関係、hydro がラグランジュ流体と ALE、radiation が FLD / SN、laser が光線追跡と沈着、materials が EOS と不透明度、coupling が演算子の時間発展、diagnostics が履歴と物理指標、drivers がコマンドの入口を担当する。tests/ は単体と統合のテスト、examples/ は利用例と検証用デッキ、docs/ は設計・仕様・数値の契約、gui/ は TENRYU Studio を収めている。変更する前に、担当するモジュールと、影響を受けるテスト・例・文書を特定すること。

単位系と namelist の契約

TENRYU の内部表現と入出力は cgs + eV である。長さ cm、時間 s、質量 g、エネルギー erg、密度 g/cm³、温度 eV という既存の契約を維持し、内部の状態を SI などへ変えることはしない。人が読み書きしやすい入力として別の単位を受け付ける場合も、境界で明示的に変換し、カーネルと状態がもつ単位、定数、式の係数を曖昧にしない実装が必要である。単位の変換を伴う変更は、数式、パーサ、凍結後の設定、入出力、検証の参照値を一体として扱う。

namelist のスキーマは厳格である。未知のブロックやキー、打ち間違い、型の違い、範囲外の値、対応していないモードの組合せは、無視や警告ではなく入力エラーにする。新しいキーには、完全修飾名、型、単位、許容範囲、相互の制約、既定値を定義すること。明示的な値を書かないデッキの挙動も API の一部なので、既定値は実装のなかに隠さず、正典となる仕様に記載する。後方互換のための別名が必要な場合も、優先順位と、競合したときのエラーを明示し、黙ってどちらかを選ぶことのないようにすること。

文書と実装を同時に変更する

このページに現れる工学上の契約書 — docs/NUMERICS.md、docs/ARCHITECTURE.md、docs/SPECIFICATION.md — は、TENRYU リポジトリにコードと並んで置かれ、ソースとともに公開されている文書である。数式、物理の係数、時間積分、空間の離散化、境界条件、単位の規約を変更する場合は、同じ変更のなかで docs/NUMERICS.md を更新する。NUMERICS.md は、実装から推測するための解説ではなく、式と離散化に関する正典の契約である。モジュールの責務やデータの流れが変わる場合は、docs/ARCHITECTURE.md も更新する。

新しい namelist のキーを追加する場合は、docs/SPECIFICATION.md §6.4 の該当スキーマと、§9.1 の既定値の一覧を、同じプルリクエストで更新する。利用者向けのページや例に影響するなら、それらも合わせて変更すること。コード、既定値、凍結後の表現、検証、文書のうち、どれかだけが先行した状態では、公開している入力の契約を再現できない。

検証と基準解

変更によって examples/verification/ の関連する検査を壊してはならない。局所的なカーネルの試験だけでなく、変更した演算子が通る解析解のケース、保存則、連成した回帰を選び、意図しない差がないことを確認する。失敗を、許容差の拡大や期待値の移動だけで消すのは修正ではない。原因を符号、単位、境界、係数、離散化、参照値のどこに求めるのかを明確にすること。

基準解の更新には、明示的な正当化が必要である。既知の不具合の修正、レビュー済みの物理・数値アルゴリズムの変更、基準となるパラメータの意図的な変更などを示し、旧値と新値の差、影響する指標、必要な収束の確認または独立な参照を記録する。単に現在の出力へ基準解を合わせることは認められない。既存の検査が確認していない新しい挙動には、新しい正解の基準または診断を追加する。

再現性の契約

決定論的な 1 次元の実運用の経路では、同じバイナリ、入力、GPU 構成のもとで、場と主要な診断量が実行のたびにビット単位で一致することを要求する。物理的な許容差をもつ回帰試験であっても、それが同じ構成での反復実行のずれを許す理由にはならない。2D RZ の一部では、多数のスレッドによる atomicAdd の加算順序に由来する、最下位ビットの差があり得る。この例外は、デッキと指標ごとに文書化した雑音帯のなかでのみ扱い、一般的な許容差として広げることはしない。

確率的な粒子の経路における乱数の系列は、粒子ごとの global_id と種、ステップによって独立に識別される。生成、複製、移送、再開の変更によって ID の空間を衝突させたり、並列の領域分割によって同じ粒子の系列を変えたりしてはいけない。乱数の分割は、保存形式や MPI を含む再現性の契約なので、局所的な最適化として変更しないこと。

Python は初期化時に凍結する

Python の namelist における関数は、読みやすい初期条件や時間波形を書くための入力の仕組みである。関数は初期化の段階でメッシュまたは時間軸の上で評価して表へ変換し、凍結後の設定と、C++ / CUDA 側が所有するデータへ移す。時間ループや GPU のカーネルから Python を呼び出す実装は追加しない。この境界によって、実行時の依存、GIL、外部状態の変化、ランクごとの評価の差を、計算から取り除ける。新しく関数を受け取る入力を追加する場合も、評価する定義域、表の解像度、ハッシュと凍結後の表現を定義すること。

プルリクエストの範囲

ひとつのプルリクエストは、ひとつの目的に限定する。不具合の修正、物理モデル、性能の調整、リファクタリング、スキーマの移行を無関係に混ぜると、数値の差の原因と検証の証拠を切り分けられない。とくに、物理の変更と性能の変更は同じプルリクエストに入れず、まず物理の契約と基準となる出力を確立し、そのうえで結果を変えない最適化として提出すること。説明には、目的、変更した契約、影響の範囲、実行した検査、検証していない構成を記載し、レビュアーが差分と証拠を一対一で追える状態にする。
