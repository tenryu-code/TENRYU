Architecture & module map reference

TENRYU is a CUDA-only code that freezes the deck into plain data during initialization, then lets clearly bounded physics modules update shared GPU-resident State. The coupling driver centrally owns operator order, time-step selection, retry, and the thermodynamic re-closure between operators; HDF5 products are consumed by TENRYU Studio and TENRYU Scope.

At a glance

  • The main computation is GPU-first and NVIDIA CUDA is the only supported backend. Module dependencies are directed and must not form cycles.
  • Python runs only while constructing the input. Callables are frozen into tables or State arrays; the time loop never calls Python (Figure A).
  • Config holds the settings built from the deck, which do not change during the run. State owns the evolving fields and the energy ledger. The coupling driver commits the state and the outputs only when an attempt at a step has passed the checks of all operators (the step is accepted; an attempt that does not pass is rejected and retried — see full-step retry).
  • Studio builds and launches decks; Scope is the companion application for inspecting and comparing HDF5 results.

Design principles and build boundary

The first principle is GPU-first execution. Hydrodynamics, radiation by flux-limited diffusion (FLD) and by discrete ordinates (SN), and laser ray tracing perform their principal work on NVIDIA GPUs; non-CUDA backends are unsupported. Three properties are requirements on the design that weigh as much as performance: locality that limits global MPI communication; fixed dependency directions among Hydro, Radiation, Laser, Materials, Mesh, Coupling, Diagnostics, I/O, and Driver; and same-GPU, same-configuration reproducibility. Future 3D and additional physics must also fit without breaking the existing boundaries.

The core uses C++20 and CUDA C++ with CMake (3.27 or newer) and Ninja. Dependencies include CUDA Toolkit 12.x (12.0 or newer), MPI 3.1+, HDF5 1.12+, Python 3.10+, and pybind11 2.11+ — the same requirement set the Building page tabulates. Embedded Python reads the deck, which is written in the namelist format of Smilei, and is released after configuration. MPI provides distributed execution, and rank 0 writes the HDF5 outputs. Physics modules interact only through the inputs and outputs they agree on (the argument data structures and the conditions that hold before and after a call) and never depend on each other's internal representations.

Module map

A module is one directory directly under src/ and the unit that separates data ownership and dependency direction; the split is a specification, not just an arrangement of directories. The term differs from a physics kernel, which is one physical operator and its page: one module can hold several physics kernels. Conduction advances as a separate operator, but its implementation lives in hydro/ and its place in the sequence belongs to coupling/.

ModuleOne-line responsibility
core/Provides configuration, deck freezing, units, errors, profiling, common device arrays, and scratch facilities used across layers.
mesh/Owns Lagrangian and ALE (arbitrary Lagrangian–Eulerian) meshes, axisymmetric (RZ) geometry, face/node connectivity, neighborhoods, and the admissibility checks of the mesh quality.
hydro/Updates momentum, position, density, ion/electron internal energy, and boundaries, and implements electron/ion conduction.
radiation/Provides 1D/2D multigroup FLD and SN, radiation sources, matter exchange, and boundary tallies.
laser/Traces refracting rays, applies inverse-bremsstrahlung absorption, and deposits energy conservatively on the Hydro mesh.
materials/Maps state to the equation of state (EOS), opacity, conductivity, relaxation times, mean ionization, and related material coefficients.
burn/Advances Bosch–Hale reaction rates, per-cell species networks, product-energy deposition, and species ledgers.
coupling/Owns operator splitting, dt selection, source injection, EOS re-closure (re-evaluating the EOS whenever an operator changes temperatures or energies, to bring the thermodynamic quantities back into consistency — see Numerical foundations), full-step retry, and the decision whether a step is accepted.
diagnostics/Builds observables for inertial confinement fusion (ICF) and audits such as energy budgets, areal density, sphericity, and shell tracking, and writes the history.
parallel/Provides MPI domain decomposition, halo exchange (the halo is the margin region that holds copies of the cells owned by neighboring ranks), and reductions over all ranks (such as the minimum time step).
verification/Provides the analytic solutions and reference values used by verification and tests (Noh, Sedov, Marshak, laser) and the audit summaries.
io/Manages the output directory and output times, and writes and reads the HDF5 snapshots and checkpoints (including restart).
drivers/Implements the run/verify entry points that assemble Config, mesh, State, and callbacks, then start the run lifecycle.

Config, State, and the coupling driver

The deck (.py) reaches the Builder through CPython and pybind11. The Builder checks types, units, ranges, and cross-field invariants before applying defaults. Geometry callables are evaluated into State arrays; waveforms and time-dependent boundaries become FrozenTable1D. The source and frozen JSON can be stored in HDF5.

Config is passed by const reference to module initialization, with only required fields copied to the GPU. State owns evolving mesh coordinates, density, velocity, 2T energies, pressures, radiation fields, deposition, and ledgers.

The coupling driver is the owner of time evolution, not another physics kernel. It takes dt as the minimum of the caps of hydro (CFL), conduction, Braginskii viscosity, nuclear burn, hot electrons, and the mixed-cell pressure relaxation (2D), together with the user cap and the caps that land on the next output time and the end time, then applies the growth limit relative to the previous accepted step (radiation and the laser propose no cap; see Time-step control & CFL). It calls laser full, burn full, hydro half, conduction full, radiation full, and hydro half, inserting required EOS synchronization and halo exchange between operators. When full-step retry is enabled, the driver snapshots State at step entry. If the hydro corrector, burn, radiation, or conduction does not accept the step, the driver restores the snapshot, shortens dt, and repeats the entire operator-split sequence (the reduction and the cap on the number of attempts are given in Time-step control & CFL). History, snapshots, checkpoints, and cumulative energy accounting are written only after a step is accepted, so rejected attempts do not become official output.

Device-memory idioms

Typed DeviceArray<T> and dimension-specific Field wrappers make ownership, moves, and reset explicit. Temporary workspaces use process-lifetime, named, grow-only scratch pools with unique tags for simultaneous buffers (device_scratch_acquire(tag, bytes)). As with cudaMalloc, an acquired buffer is not zero-filled, so a CUDA kernel that needs zeros clears the buffer explicitly. Pooled wrappers do not free individually; shutdown releases the pools together. This convention removes repeated time-loop allocation while preventing aliasing and dependence on old contents. Short-lived buffers come from a stream-ordered memory pool (device_pool_malloc, built on cudaMallocAsync and cudaFreeAsync), so that allocation and release do not synchronize the device.

The two desktop applications

TENRYU Studio — build and run

TENRYU Studio is a Tauri 2 and React/TypeScript form-based deck application. It configures the run and generates a Python deck with embedded state for round-trip editing. It validates decks and uses system ssh/scp for configured servers. Its final artifact is the same single deck that the CLI accepts.

TENRYU Scope — inspect and compare

TENRYU Scope specializes in HDF5 snapshots and history. It opens local or remote runs, then renders 1D profiles, histories, and 2D tensor or CSR (compressed-sparse-row connectivity) multiblock fields. It provides colormaps, linear/log ranges, zoom/pan, time animation, lineouts, laser-ray overlays, and PNG, CSV, or video export. Scope does not replace the lightweight result check in Studio; it takes on large-field exploration and run-to-run comparison.
