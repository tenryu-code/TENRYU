Developer guide reference

A TENRYU contribution should make its physics, input specification, implementation, verification, and documentation one traceable change. Fixing the internal unit system to cgs + eV, checking namelist keys strictly, not breaking the existing verification tests, making runs of the same configuration return the same result every time, and not calling Python after initialization are not matters to defer until after performance or convenience work; they are conditions that every change must satisfy.

At a glance

  • The internal unit system is fixed to cgs + eV; do not replace it with SI or another internal representation.
  • Unknown namelist keys are errors, and every key must document its type, units, constraints, and default.
  • Update NUMERICS.md with equation or discretization changes and SPECIFICATION.md with new keys.
  • Deterministic 1D paths and 2D RZ paths must reproduce bitwise between replicas of the same configuration, and each particle's random-number stream remains independent through global_id.

Repository layout

The principal implementation lives under src/: core owns state, configuration, and units; mesh geometry and mesh topology; hydro Lagrangian hydrodynamics and ALE (arbitrary Lagrangian–Eulerian); radiation FLD (flux-limited diffusion) and SN (discrete ordinates); laser ray tracing and deposition; materials EOS (equation of state) and opacity; coupling operator evolution; diagnostics histories and physics metrics; and drivers command entry points. tests/ contains unit and integration tests, examples/ user examples and verification decks, docs/ design and numerical-method documents, and gui/ TENRYU Studio. Identify the owning module and affected tests, examples, and documents before editing.

Units and namelist specification

TENRYU's internal state and I/O use cgs + eV: cm for length, s for time, g for mass, erg for energy, g/cm³ for density, and eV for temperature. Do not convert internal state to SI or another unit system. A human-facing input may accept another unit only by converting explicitly at its boundary; physics-kernel units, constants, and equation coefficients must remain unambiguous. Treat a unit-bearing change as one change across equations, parser, frozen configuration, I/O, and verification references.

The namelist schema is strict. Unknown blocks or keys, misspellings, wrong types, out-of-range values, and unsupported mode combinations must be input errors—not ignored values or warnings. Every new key requires a fully qualified name, type, units, valid range, cross-field constraints, and default. Behavior when a deck omits the key is also part of the public input specification, so defaults belong in the authoritative specification rather than only in implementation. If compatibility aliases are necessary, document precedence and reject conflicting forms instead of silently choosing one.

Change documentation with implementation

The design documents named on this page — docs/NUMERICS.md, docs/ARCHITECTURE.md, and docs/SPECIFICATION.md — live in the TENRYU repository beside the code, publicly readable with the source. Any change to an equation, physical coefficient, time integration, spatial discretization, boundary condition, or unit convention must update docs/NUMERICS.md in the same contribution. NUMERICS.md is the authoritative document for equations and discretization (the reference that the implementation follows), not commentary reconstructed later from code. Update docs/ARCHITECTURE.md as well when module ownership or data flow changes.

Adding a namelist key requires updating, in the same pull request, both the applicable schema in docs/SPECIFICATION.md §6.4 and the authoritative default list in §9.1. Update user pages and examples when behavior exposed there changes. Code, defaults, frozen configuration, verification, and documentation must land together; omitting one leaves the public input specification unreproducible.

Verification and goldens

Changes must not break the relevant gates under examples/verification/. In addition to local physics-kernel tests, select the analytic case, conservation check, and coupled regression traversed by the changed operator. The kinds of checks and their criteria are described on the verification and benchmarks page. Do not erase a failure merely by widening a tolerance or moving an expected value. Determine whether its cause is a sign, unit, boundary, coefficient, discretization, or reference issue.

A golden (the reference values saved from an approved run; the definition is in the legend of the verification page) is re-baselined with tenryu verify gxii_1d_fld_regression --generate-golden. Golden updates require explicit justification: for example, a known bug fix, a reviewed physics or numerical-algorithm change, or an intentional baseline-parameter change. Record old-to-new differences, affected metrics, and any required convergence or independent reference. A failing current output is not itself a reason to rebaseline. New behavior outside existing gate coverage needs a new oracle or diagnostic.

Reproducibility requirements

Deterministic one-dimensional production paths must produce bitwise-identical fields and principal diagnostics with the same binary, input, and GPU configuration. A physical tolerance in a regression does not permit drift between same-configuration replicas. In 2D RZ as well, the floating-point sums within a step have been replaced by fixed-order sums, and two runs of the same configuration must agree bitwise in the state, the time step, the energy ledgers, and the diagnostics. A change that adds an order-dependent atomicAdd must either use a fixed-order sum or record the reason the call is order-independent in tools/checks/atomic_add_allowlist.json (ctest -R atomic_add_allowlist rejects calls missing from the list). A band that accepts differences between replicas (a noise band) may be used only for a path whose sum cannot be put in fixed order, only within a documented band for each deck and metric, and must not be generalized into a broad tolerance (see the verification page for the definition of the band).

For stochastic particle paths, each RNG stream is independently identified through particle global_id, seed, and step. Generation, duplication, migration, and restart changes must not collide ID ranges or make a particle's stream depend on parallel decomposition. RNG partitioning is a reproducibility requirement spanning storage and MPI, not a local optimization detail.

Freeze Python inputs at initialization

Python namelist callables are an input convenience for describing initial conditions and time waveforms. Evaluate them over their mesh or time domain during initialization, tabulate them, and transfer the result into the frozen configuration and C++/CUDA-owned data. Do not add Python calls to the time loop or to a CUDA kernel. This boundary excludes runtime dependencies, the GIL (Python's global interpreter lock), mutable external state, and rank-dependent evaluation from the simulation. A new callable input must define its evaluation domain, table resolution, hash, and the representation in the frozen configuration.

Pull-request scope

One pull request should have one purpose. Mixing an unrelated bug fix, physics model, performance tuning, refactor, and schema migration makes numerical differences and verification evidence impossible to isolate. In particular, do not combine physics changes with performance work: establish the physical specification and baseline first, then submit optimization as a result-preserving change. State the purpose, changed specifications and criteria, impact, gates run, and untested configurations so reviewers can map every part of the diff to evidence. External contributors should discuss the intended change in GitHub Issues before starting work (under the license, publishing or redistributing modified versions requires written permission).
