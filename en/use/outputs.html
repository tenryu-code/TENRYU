Outputs & analysis reference

One TENRYU run produces three kinds of HDF5 — snapshots (spatial fields), a history (scalar time series), and checkpoints (for restart) — plus provenance files (the frozen configuration, run info, logs). This page lists what gets written: file kinds and naming, the snapshot groups and their main datasets, the main history channels, the checkpoint additions, and how to read them. The canonical source including dtypes and array shapes is docs/SPECIFICATION.md §7 in the repository (summarized in docs/OUTPUT_SCHEMA.md). Terms specific to reading these outputs are defined in the terms section.

At a glance

  • Three HDF5 kinds: snapshots <name>_NNNN.h5, the history <name>_history.h5 (append-only), and checkpoints <name>_ckpt_NNNN.h5. Cadence fires on step-based (plot_every …) OR seconds-based (plot_every_s …) triggers.
  • Every numeric dataset carries a units attribute. mesh/ and hydro/ dataset names map 1:1 to the internal State field names.
  • Stagnation peaks are short — about 15 ps in a GXII (GEKKO XII)-class laser implosion run of 2026-07-31 — so peak values are read from the per-step history (implosion/*), not from snapshots.
  • Re-running into the same output directory does not overwrite: results go to a numbered sibling like _001. If "nothing changed", check the output location first.

<name> is Main.name, falling back to the file name of the deck (definition) without its extension. In MPI (message passing interface) runs, rank 0 (MPI process number 0) writes the snapshots, the history, and the checkpoints; no per-rank files are written. The directory layout:

outputs/<name>/
├── results/                  ← snapshots and history
│   ├── <name>_0000.h5
│   ├── <name>_0001.h5
│   └── <name>_history.h5
├── config/                   ← provenance (frozen configuration, deck copy)
│   ├── <name>_frozen.json
│   └── <name>_namelist.py
├── checkpoints/              ← for restart
│   └── <name>_ckpt_0000.h5
├── log/                      ← run logs (tenryu.log)
├── run_info.json             ← run summary (termination state etc.)
└── mesh_requirement.json     ← verdict on the initial-mesh resolution requirement (fresh 1D runs only)

The number in the names of the snapshot and checkpoint files counts the files written to that output directory in order, starting from 0; it is not the step number. For example, the first checkpoint of a run that writes a checkpoint every 100 steps is <name>_ckpt_0000.h5. The step number is in the root attribute step (the same value is also written as cycle). When a run is stopped by placing a file named stop_request in the output directory, the checkpoint goes to checkpoints/ as event_stop_<step number>.h5, named by the step number instead of a sequence number; checkpoint_keep_last does not delete it.

mesh_requirement.json is written by fresh 1D runs only. It records the estimate and the verdict of whether the initial mesh meets the resolution that the physics requires. When the requirement does not apply (for example, the laser is disabled), applicable is false and reason gives the reason.

If the output directory already exists and collides, nothing is overwritten: results are written to a 3-digit numbered sibling such as outputs/<name>_001/. To redirect output without editing the deck, use tenryu run <deck> --output-dir <dir> (new runs only; combining with a restart is a ConfigError).

Terms used in this page

The terms specific to reading these outputs are defined below: the artificial terms of the energy ledger, provenance and the frozen configuration, the shell radius, thickness, IFAR, and convergence ratio, and the hotspot gas with its radii. The constraint that set Δt (the "winner" in the history channel dt_winner and similar names) is defined in Time-step control.

The energy ledger and its artificial terms

The energy ledger is the identity that, at every step, matches the change of the total energy of the system against the terms for energy entering, leaving, and being corrected. Each channel of energy/ in the history holds one of these terms, and conservation_error is its relative error ε_budget. The identity and the definition of each term are in the energy-ledger section of the numerical foundations. The four terms below book the energy that numerical operations added to the state.

The floor correction is the sum of the energy that each operator added to raise the energy itself to its lower bound (floors, clamps, and safety guards). floor_injected is the run-cumulative value and floor_injected_step is this step's value.

The safety correction is the slot that books the safety correction of conduction. The current implementation books the conduction corrections in the floor correction and gives this slot the same value as the floor correction, so safety_injected equals floor_injected.

The unresolved ALE redistribution is the sum of two energies in the 2D RZ ALE (arbitrary Lagrangian–Eulerian) remap: the energy difference when a cell that fell to the mass floor is put into the floor state, and the shortfall that the redistribution of the kinetic-energy closure (Numerics.ale.ke_closure_redistribute_floor, default False) could not absorb. It is zero without ALE. redistribution_unresolved holds only this step's value.

The solver residual is the slot that books the residual of the implicit solver with its sign. No operator adds to it, so solver_residual is always 0. A nonzero value would enter the ledger as an inflow or an outflow according to its sign.

In ε_budget, the sum of the floor correction and the unresolved ALE redistribution is subtracted from the total-energy change as the artificial term (the safety correction is not added because it equals the floor correction). The artificial term is energy that numerical operations brought in, not a physical inflow or outflow, so it does not count in ε_budget. A warning is issued when ε_budget exceeds Diagnostics.energy_budget.warn_threshold (default \(10^{-3}\); the first step is not checked). The floor correction, the safety correction, and the unresolved ALE redistribution each warn when their ratio to the energy scale at the start of the step, E_denom, exceeds \(10^{-3}\). When ε_budget jumps, look at the ratio of the artificial terms first. If they dominate, suspect where floors and clamps are triggered; otherwise suspect the attribution of boundaries and sources (absorption fraction, escape).

Provenance and the frozen configuration

Provenance is the record that lets you check later which input and which execution environment produced an output. TENRYU keeps as provenance the copy of the deck config/<name>_namelist.py (Output.save_namelist_copy, default True), the frozen-configuration JSON config/<name>_frozen.json (Output.save_frozen_config, default True), the run summary run_info.json, the run log log/tenryu.log, and the metadata/ group of each HDF5 file (the full deck text namelist_source, the frozen configuration frozen_config, the radiation group edges group_bounds_eV, and so on). It is the primary audit of what the run actually received, not of what you think you typed. The provenance section describes each file. When a restart is not an exact continuation of the original run, the root attribute restart_provenance records the mark so that the output of the restarted run can be told from that of a continued run. The group diagnostics/ale_provenance/v1/, whose name also contains "provenance", is a different record: it states whether the ALE settings followed the standard profile (see the history tables).

The frozen configuration is the configuration fixed at initialization, after Python functions are tabulated and defaults are filled in. It is defined on the running page. The provenance keeps it in two forms: config/<name>_frozen.json, which holds the whole resolved configuration and a summary of the runtime values, and the HDF5 dataset metadata/frozen_config, which is used to check a restart. The HDF5 attribute git_hash is always "unknown", so the commit that was run cannot be read from the HDF5 file. _tenryu_version in config/<name>_frozen.json is the number of the released version.

Shell radius, thickness, IFAR, and convergence ratio

The shell is the dense outer layer of the imploding capsule. The group diagnostics/icf/v1/ of the history measures its position and shape from the density distribution by the rules below, stated for 1D. \(\rho_{peak}\) is the maximum density over all cells.

The shell radius \(R_{shell}\) (shell_radius_cm) is the mass-weighted mean of the cell-center radius (the average of the radii of the two nodes of the cell) over the cells with \(\rho\ge0.1\rho_{peak}\).

The shell thickness \(\Delta R_{shell}=R_{outer}-R_{inner}\) (shell_thickness_cm) uses \(R_{outer}\), the radius of the outer node of the outermost cell whose density is at least the outer threshold, and \(R_{inner}\), the radius of the inner node of the innermost cell whose density is at least the inner threshold. The thresholds are set by Numerics.diagnostics.icf.rho_outer_threshold_g_per_cc and rho_inner_threshold_g_per_cc; with 0 (default) the outer threshold is 0.1 \(\rho_{peak}\) and the inner one is 0.5 \(\rho_{peak}\).

The IFAR (in-flight aspect ratio) \(\mathrm{IFAR}=R_{shell}/\Delta R_{shell}\) (IFAR) is larger for a thinner shell.

The convergence ratio (CR) \(\mathrm{CR}=R_{initial}/R_{shell}\) (CR) uses \(R_{initial}\), the shell radius at the first step at which the shell could be measured, which is written as the attribute R_initial_cm of diagnostics/icf/v1/ in the history. The first value of CR is 1, and it grows as the shell shrinks. A restarted run reads \(R_{initial}\) back from the history file of the run it restarts from.

On a 2D structured mesh, \(R_{shell}\) uses the r coordinate of the cell (the average of r of its two nodes) as the weighting radius, and \(R_{outer}\) and \(R_{inner}\) are found from the density on the equatorial line (\(z=0\)), which is divided into 1024 intervals from r = 0 to the outer edge (\(R_{inner}\) is the first point, seen from the center, where the density crosses the inner threshold, found by linear interpolation). The history channel implosion/shell_radius_mean is the mass-weighted mean of the cell-centroid radius over the same cells with \(\rho\ge0.1\rho_{peak}\). The two values differ by the difference between the centroid and the midpoint.

Hotspot gas and R50…R99

The hotspot gas is the gas that was in the central part of the target at the start, marked with a passive tracer that is carried with the flow. With Numerics.diagnostics.hotspot_gas.enabled=True, at step 0 the tracer \(Y_g=1\) is set in the cells whose centroid distance from the center, \(\sqrt{r^2+z^2}\) (\(r\) in 1D), is smaller than Numerics.diagnostics.hotspot_gas.R_g_cm (\(R_g\) [cm]; set it above 0 when enabled), and 0 in the other cells. In Lagrangian hydrodynamics the tracer moves with the cell; in the ALE remap the mass \(mY_g\) is carried with the same upwind rule and limiter as the fluid mass flux. The value is kept in hydro/gas_tracer_Y. The mass first marked is gas_mass_initial_g; the relative difference of the mass \(M_g=\sum_c m_cY_{g,c}\) at each time from its initial value is gas_mass_rel_drift, and a warning is issued when its absolute value exceeds Numerics.diagnostics.hotspot_gas.mass_drift_warn_rel (default \(10^{-10}\)).

The gas radii R50, R90, R95, and R99 are quantiles of the radius weighted by the gas mass. Sort the cells that hold the tracer in ascending order of the centroid distance from the center; the distance of the first cell at which the cumulative mass \(mY_g\) reaches p % of \(M_g\) (p = 50, 90, 95, 99) is \(R_{p}\) (R50_cm, R90_cm, R95_cm, R99_cm). The gas convergence ratio \(\mathrm{CR}_{p}=R_g/R_{p}\) (CR50, CR90, CR95, CR99) is the initial radius \(R_g\) divided by the current radius. It is a different quantity from the shell convergence ratio CR. The initial value of \(\mathrm{CR}_{50}\) is not 1 (it is \(2^{1/3}\simeq1.26\) for a sphere of uniform density), so C_R50_norm, divided by that initial value, is also written.

The other quantities are defined as follows. The rms radius \(R_{rms}=\sqrt{(5/3)\langle r^2\rangle}\) (Rrms_cm; equal to the radius of a uniform sphere) and its convergence ratio CRrms. The cube root CR_V of the ratio to its initial value of the volume-mean density of the gas, \(M_g/\sum_c Y_{g,c}V_c\) (rho_bar_volume_gcc). The cube root CR_rho50 of the ratio to its initial value of the mass-median density of the gas, rho50_gcc. The mass-weighted mean and quantiles of the pressure \(p\) (electron + ion) and of the adiabat quantity \(K=p/\rho^{\gamma}\) (K_mean, K50, K90, K95, K99; \(\gamma\) is the adiabatic index of the first non-void ideal-gas material, or 5/3 if none can be defined). The mass-weighted mean and p10, p50, p90 of the electron and ion temperatures (the ion temperature only in two-temperature runs). The energies (internal, kinetic, total) and the work proxy hotspot_work_proxy_*_erg, their change from the initial values. The work proxy is the change of the total energy \(\sum_c Y_gm(e_e+e_i+\tfrac12|\mathbf{u}|^2)\) of the region defined by the tracer, not the integral of the pressure work at its boundary (hotspot_work_definition holds the same definition).

Snapshot datasets

Root attributes: t (time [s]), dt (Δt [s]), cycle and step (both are the step number), geometry ("1D_SPH"|"2D_RZ"), nr and nz (Mesh.nr and, in 2D, Mesh.nz; nz is 1 in 1D), n_cells, n_nodes, n_groups, n_materials, two_temperature (always 1), schema_version. When a restart is not an exact continuation of the original run (for example, when the checkpoint has no state file for Numerics.ale.band_ale, the file named like the checkpoint with .band-state appended), the run writes a mark to the string root attribute restart_provenance (for example, RESTART_WITHOUT_BAND_STATE). Because geometry reads "1D_SPH" for every 1D geometry, 1D files also carry geometry_1d ("spherical"|"cylindrical"|"planar"). In 1D, arrays are flat and mesh/x_z, v_z are omitted. History channels

results/<name>_history.h5 is append-only. This page calls each time series of the history a channel. The root holds the three series t, cycle, and dt; the stop reason is recorded as termination_reason in run_info.json (for example "t_end_reached" or "max_steps_reached").

Warning: cadence can miss the peak

Snapshot cadence is per-deck, but stagnation peaks can be very short — about 15 ps measured (2026-07-31) in a GXII-class laser implosion run. When output times straddle the peak, the maximum density among snapshots badly underestimates the true peak. Read sharp peak values and times from the per-step history (implosion/rho_peak) and use snapshots for the spatial structure around the peak.

Checkpoint additions and restart compatibility

Checkpoints store the snapshot content plus the internal state needed to resume.

GroupContent
hydro_flags/hydro_activePer-cell hydro activity mask.
time_state/The step, t, and dt that the snapshot also holds, plus the cumulative energy terms and user_seed (the value of Main.seed). The restart Δt comes from here. A restart is refused with a ConfigError when Main.seed differs from user_seed.
output_state/Next scheduled output times (t_next_plot, t_next_history, t_next_checkpoint).
hydro/cv_e, cv_i, cs (1D)Heat capacities and sound speed obtained from the equation of state (EOS). A 1D restart from a checkpoint that has them does not redo the re-closure (definition), and the restarted run continues bitwise identical to the original run (except runs that reuse ray traces, Laser.raytrace_skip_config.enabled=True).
hydro_flags/cell_is_void (1D)Flags that mark the void cells (cells of a Material.is_void material; definition). A 1D run always writes it (zeros when there are no void cells); a 2D run writes it only when the run holds the mask.

burn_state/specific_inventoryNuclear-burn specific inventories \(Y_s\) [1/g] (per cell D, T, He3, He4, p). A restart uses these rather than the snapshot number densities hydro/burn_n_* divided by the density (since 2026-09-26).

Restart compatibility: a checkpoint with the current schema_version (2 since 2026-09-29) is read normally, one with an older (or missing) version is read with backward-compatible defaults, and one with a newer version is refused. A restart is refused when the checkpoint's frozen configuration (the hash of the deck text and every setting except Main.restart_from) does not match the restarting deck. The running page explains how to specify a restart.

Provenance: frozen-configuration JSON, run_info, logs

config/<name>_frozen.json is a JSON of the fully resolved configuration (the sections main, mesh, materials, laser, numerics, and so on, in which a Python function is recorded by its name, repr, and source_hash, the hash of its source code), plus the TENRYU version _tenryu_version, the UTC time of the freeze _frozen_at, the hash of the deck text _namelist_source_hash, and frozen_summary. frozen_summary holds the initial density (minimum, maximum, and mean), electron and ion temperatures (minimum and maximum), the volume of each material, and, for each function frozen into a table at initialization, the time range (t_min and t_max), the point count n_points, the peak peak_value, and the integral integrated_value. The HDF5 dataset metadata/frozen_config is the same configuration without _tenryu_version, _frozen_at, and frozen_summary. A value overridden by --output-dir (a fresh run) or --t-end and --max-steps (a restart) enters config/<name>_frozen.json as the value actually used, while metadata/frozen_config keeps the value of the deck. It is the primary audit of what the run actually received (rather than what you think you typed); keep it with the deck for reproduction and comparison. run_info.json summarizes the run and log/ holds the run logs. When you doubt that a setting took effect, read the frozen-configuration JSON first, then the warnings in the log.

Reading the data: CLI, bundled tools, Scope

Structure inspection needs only the standard HDF5 tools:

h5ls  outputs/<name>/results/<name>_0010.h5          # group listing
h5dump -H outputs/<name>/results/<name>_history.h5  # header structure

The fastest plots come from the bundled tenryu_plot (tools/), with subcommands including profile (spatial profiles), history (time series), spacetime, summary, compare, and spectrum:

python3 -m tools.tenryu_plot --help                  # list
python3 -m tools.tenryu_plot profile outputs/<name>  # spatial profiles
python3 -m tools.tenryu_plot history outputs/<name>  # time series

For direct reading, h5py is shortest. Every numeric dataset has a units attribute, and array lengths follow the field layout (cells, nodes, cells×materials, cells×radiation groups) — read root attributes, shapes, and units together:

import h5py
f = h5py.File("outputs/<name>/results/<name>_0010.h5")
Te = f["hydro/Te"][:]; r = f["mesh/x_r"][:]
print(f["hydro/Te"].attrs["units"])   # -> "eV"

For interactive exploration and run-to-run comparison, use TENRYU Scope (see Architecture). Find the interesting times and quantities in the viewer, then make the final figures from the frozen configuration and explicit script arguments to combine interactivity with reproducibility.
