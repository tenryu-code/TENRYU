Outputs & analysis reference

One TENRYU run produces three kinds of HDF5 — snapshots (spatial fields), a history (scalar time series), and checkpoints (for restart) — plus provenance files (the frozen configuration, run info, logs). This page gives the overview of the outputs: file kinds, naming, cadence, and the layout of the output directory; the provenance files; and how to read the data (CLI, bundled tools, Scope). The contents of the three HDF5 kinds are listed on the pages Snapshots, History, and Checkpoints and restart. The canonical source including dtypes and array shapes is docs/SPECIFICATION.md §7 in the repository (summarized in docs/OUTPUT_SCHEMA.md). The terms of provenance used on this page are defined in the terms section.

At a glance

  • Three HDF5 kinds: snapshots <name>_NNNN.h5, the history <name>_history.h5 (append-only), and checkpoints <name>_ckpt_NNNN.h5. Cadence fires on step-based (plot_every …) OR seconds-based (plot_every_s …) triggers.
  • Every numeric dataset carries a units attribute. mesh/ and hydro/ dataset names map 1:1 to the internal State field names.
  • Stagnation peaks are short — about 15 ps in a GXII (GEKKO XII)-class laser implosion run of 2026-07-31 — so peak values are read from the per-step history (implosion/*), not from snapshots.
  • Re-running into the same output directory does not overwrite: results go to a numbered sibling like _001. If "nothing changed", check the output location first.

Snapshots

The root attributes and the datasets of the metadata, mesh, hydro, diagnostics, radiation, and laser groups.

History

The channels of energy, the physics summary, laser, radiation, and more, and the terms of the energy ledger, the shell, and the hotspot gas.

Checkpoints and restart

The groups added for restart and the restart compatibility rules by schema_version and the frozen configuration.

Files, naming, cadence

FileNamingCadencePurpose
Snapshot<name>_NNNN.h5 (4-digit zero-padded sequence number)every plot_every steps or every plot_every_s seconds (OR logic)Field visualization and post-processing. Physical time in root attribute t, step number in step (the same value is also written as cycle).
History<name>_history.h5history_every / history_every_s (OR, appended)Scalar diagnostics time series; extensible datasets appended each output.
Checkpoint<name>_ckpt_NNNN.h5 (4-digit zero-padded sequence number)checkpoint_every / checkpoint_every_s (OR)Used to restart a run. Only checkpoint_keep_last files are kept; older ones are deleted automatically.

<name> is Main.name, falling back to the file name of the deck (definition) without its extension. In MPI (message passing interface) runs, rank 0 (MPI process number 0) writes the snapshots, the history, and the checkpoints; no per-rank files are written. The directory layout:

outputs/<name>/
├── results/                  ← snapshots and history
│   ├── <name>_0000.h5
│   ├── <name>_0001.h5
│   └── <name>_history.h5
├── config/                   ← provenance (frozen configuration, deck copy)
│   ├── <name>_frozen.json
│   └── <name>_namelist.py
├── checkpoints/              ← for restart
│   └── <name>_ckpt_0000.h5
├── log/                      ← run logs (tenryu.log)
├── run_info.json             ← run summary (termination state etc.)
└── mesh_requirement.json     ← verdict on the initial-mesh resolution requirement (fresh 1D runs only)

The number in the names of the snapshot and checkpoint files counts the files written to that output directory in order, starting from 0; it is not the step number. For example, the first checkpoint of a run that writes a checkpoint every 100 steps is <name>_ckpt_0000.h5. The step number is in the root attribute step (the same value is also written as cycle). When a run is stopped by placing a file named stop_request in the output directory, the checkpoint goes to checkpoints/ as event_stop_<step number>.h5, named by the step number instead of a sequence number; checkpoint_keep_last does not delete it.

mesh_requirement.json is written by fresh 1D runs only. It records the estimate and the verdict of whether the initial mesh meets the resolution that the physics requires. When the requirement does not apply (for example, the laser is disabled), applicable is false and reason gives the reason.

If the output directory already exists and collides, nothing is overwritten: results are written to a 3-digit numbered sibling such as outputs/<name>_001/. To redirect output without editing the deck, use tenryu run <deck> --output-dir <dir> (new runs only; combining with a restart is a ConfigError).

Terms used in this page

The terms of provenance used on this page are defined below: provenance and the frozen configuration. The artificial terms of the energy ledger, the shell radius, thickness, IFAR, and convergence ratio, and the hotspot gas are defined in the terms section of the History page.

Provenance and the frozen configuration

Provenance is the record that lets you check later which input and which execution environment produced an output. TENRYU keeps as provenance the copy of the deck config/<name>_namelist.py (Output.save_namelist_copy, default True), the frozen-configuration JSON config/<name>_frozen.json (Output.save_frozen_config, default True), the run summary run_info.json, the run log log/tenryu.log, and the metadata/ group of each HDF5 file (the full deck text namelist_source, the frozen configuration frozen_config, the radiation group edges group_bounds_eV, and so on). It is the primary audit of what the run actually received, not of what you think you typed. The provenance section describes each file. When a restart is not an exact continuation of the original run, the root attribute restart_provenance records the mark so that the output of the restarted run can be told from that of a continued run. The group diagnostics/ale_provenance/v1/, whose name also contains "provenance", is a different record: it states whether the ALE settings followed the standard profile (see the tables on the History page).

The frozen configuration is the configuration fixed at initialization, after Python functions are tabulated and defaults are filled in. It is defined on the running page. The provenance keeps it in two forms: config/<name>_frozen.json, which holds the whole resolved configuration and a summary of the runtime values, and the HDF5 dataset metadata/frozen_config, which is used to check a restart. The HDF5 attribute git_hash is always "unknown", so the commit that was run cannot be read from the HDF5 file. _tenryu_version in config/<name>_frozen.json is the number of the released version.

Provenance: frozen-configuration JSON, run_info, logs

config/<name>_frozen.json is a JSON of the fully resolved configuration (the sections main, mesh, materials, laser, numerics, and so on, in which a Python function is recorded by its name, repr, and source_hash, the hash of its source code), plus the TENRYU version _tenryu_version, the UTC time of the freeze _frozen_at, the hash of the deck text _namelist_source_hash, and frozen_summary. frozen_summary holds the initial density (minimum, maximum, and mean), electron and ion temperatures (minimum and maximum), the volume of each material, and, for each function frozen into a table at initialization, the time range (t_min and t_max), the point count n_points, the peak peak_value, and the integral integrated_value. The HDF5 dataset metadata/frozen_config is the same configuration without _tenryu_version, _frozen_at, and frozen_summary. A value overridden by --output-dir (a fresh run) or --t-end and --max-steps (a restart) enters config/<name>_frozen.json as the value actually used, while metadata/frozen_config keeps the value of the deck. It is the primary audit of what the run actually received (rather than what you think you typed); keep it with the deck for reproduction and comparison. run_info.json summarizes the run and log/ holds the run logs. When you doubt that a setting took effect, read the frozen-configuration JSON first, then the warnings in the log.

Reading the data: CLI, bundled tools, Scope

Structure inspection needs only the standard HDF5 tools:

h5ls  outputs/<name>/results/<name>_0010.h5          # group listing
h5dump -H outputs/<name>/results/<name>_history.h5  # header structure

The fastest plots come from the bundled tenryu_plot (tools/), with subcommands including profile (spatial profiles), history (time series), spacetime, summary, compare, and spectrum:

python3 -m tools.tenryu_plot --help                  # list
python3 -m tools.tenryu_plot profile outputs/<name>  # spatial profiles
python3 -m tools.tenryu_plot history outputs/<name>  # time series

For direct reading, h5py is shortest. Every numeric dataset has a units attribute, and array lengths follow the field layout (cells, nodes, cells×materials, cells×radiation groups) — read root attributes, shapes, and units together:

import h5py
f = h5py.File("outputs/<name>/results/<name>_0010.h5")
Te = f["hydro/Te"][:]; r = f["mesh/x_r"][:]
print(f["hydro/Te"].attrs["units"])   # -> "eV"

For interactive exploration and run-to-run comparison, use TENRYU Scope (see Architecture). Find the interesting times and quantities in the viewer, then make the final figures from the frozen configuration and explicit script arguments to combine interactivity with reproducibility.
