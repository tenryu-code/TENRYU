Namelist reference

This page is an orientation map, not an exhaustive specification of the namelist, the format in which a deck (the one Python file that is the input to TENRYU) is written. It connects top-level blocks and important sub-blocks to representative keys. The complete key specification — types, units, accepted values, combination rules, and the authoritative default list — lives in the specification shipped with the source: docs/SPECIFICATION.md §6.4 (schema) and §9.1 (defaults) in the TENRYU repository, which is publicly readable alongside the code. The definitions of deck, namelist, block, sub-block, and key are in the terms section.

At a glance

  • The 11 blocks, from Main through Parallel, divide case identity, mesh, materials, initialization, physics, numerics, and output responsibilities.
  • A key whose value is a dict is a sub-block with its own set of keys. For example, Numerics.dt.max_s and Numerics.hydro.av_C2 are keys of different sub-blocks, dt and hydro, and the values they accept are checked separately.
  • Unknown keys, wrong types, out-of-range values, and unsupported block combinations are input errors. A typo does not silently fall back to a default. The exception is a small number of keys that are accepted for compatibility, draw a WARNING, and do nothing (Validation and defaults).
  • The keys below are entry points, not complete lists. This page's tables deliberately omit defaults; the per-kernel pages list selected defaults, and where they disagree with SPECIFICATION §9.1, §9.1 is authoritative.

Terms used in this calculation

This page and the pages that link here use the five words deck, namelist, block, sub-block, and key in the senses below.

Deck and namelist

A deck is one Python file, the input that is given to TENRYU. The argument of tenryu run deck.py or tenryu validate deck.py is a deck, and all the conditions of one calculation — mesh, materials, initial conditions, physics, numerical methods, and output — are written in this single file. A deck is run as an ordinary Python script, so it may define functions and constants and read environment variables. TENRYU runs the deck once in an embedded Python interpreter. Each block function that the deck calls checks the names and values of its keys on the spot and registers them, and after the deck has finished, TENRYU runs the checks that span blocks and fixes the configuration. The repository's docs/SPECIFICATION.md §6 calls this file a namelist.

The namelist is the format of the deck. The format is defined by the block functions that the tenryu_namelist module provides and by the keys these functions accept. The module is built into the TENRYU executable, and a deck begins with from tenryu_namelist import * to use the block functions. This site calls the file the deck and the format the namelist. This page is a guide to the keys of the namelist.

Blocks and sub-blocks

A block is a top-level unit of settings in a deck, called as a Python function of the same name (a block function). There are 11: Main, Mesh, Materials, Geometry, Radiation, Laser, Numerics, Output, Diagnostics, Parallel, and Burn. A block function receives its settings as keyword arguments (key = value) and only registers the values with TENRYU; its return value is not used.

Main, Mesh, Materials, and Geometry are required; without one of them, the check of the deck stops with Required block not provided. The other blocks may be omitted, and every key of an omitted block takes its default. For example, the default of Radiation.enabled is True, so a deck that does not use radiation writes Radiation(enabled=False). Each block is called once; a second call prints a WARNING, and the later call overwrites the earlier values.

Material(...) and LaserBeam(...) are not blocks but helper functions that return a dict (dictionary). The Material dicts go into the list of Materials(materials=[...]), and the LaserBeam dicts into the list Laser.beams.

A sub-block is a dict written as the value of a key of a block, which itself accepts its own set of keys. The dt=dict(max_s=…, min_s=…) of Numerics is an example, called Numerics.dt. A sub-block may contain further sub-blocks (Numerics.ale.band_ale). The dicts returned by Material(...) and LaserBeam(...) are also sub-blocks, passed as list elements.

Keys

A key is the name of a setting passed to a block or sub-block. The name of a keyword argument of a block function (t_end in Main(t_end=…)) and the name of a key of a sub-block's dict (max_s in dt=dict(max_s=…)) are both keys. Because keys of the same name exist in several blocks (enabled, for one), a key is called by its fully qualified name, the block name and sub-block names joined by . (Numerics.conduction.enabled). Each name is checked against the set of names that the block or sub-block accepts, and a name outside the set is an input error (Validation and defaults).

A deck normally imports tenryu_namelist and calls each block function once. Material(...) returns a dict; collect these dicts and register them through Materials(materials=[...]). Reading key paths

Think in fully qualified names (keys) when similarly named controls appear in several places. Radiation.enabled, Numerics.conduction.enabled, and Burn.enabled are separate switches. Radiation boundary keys are another important example: some belong to the selected solver's mode-specific sub-block, while other drive controls belong to top-level Radiation.boundary. Do not infer nesting from the final key name; consult the matching §6.4 block.

Values use the cgs + eV system: length in cm, time in s, density in g/cm³, and temperatures and photon-group edges in eV. A key that names another unit — such as wavelength_nm or T_floor_keV — takes its unit from the suffix. Units, exact types, and dimension-specific restrictions are intentionally omitted from this map and must be checked before entering production values.

Validation and defaults

The parser applies known-key validation at every hierarchy level. It does not discard unknown keys and continue. Wrong types, missing required values, invalid ranges, mutually exclusive modes, and settings unsupported for the selected dimension or MPI rank count stop the run as input errors. An error is reported as a ConfigError or ValueError exception, and both are printed on a line that begins with TENRYU ERROR [namelist]:. This check prevents a configuration typo from appearing later as an unexplained physics result.

The exception is a key that is accepted only for compatibility and does nothing. Accepting it prints a WARNING that says the key has no effect. For example, Numerics.dt.f_min_fleck and Numerics.safety.opacity_floor and opacity_cap are keys of the Monte Carlo radiation, which is not part of the current build. Diagnostics.shell also does nothing (the diagnostics of the shell are made by Numerics.diagnostics.icf).

Authoritative full reference and defaults

This page is only an orientation map. The authoritative full key reference is docs/SPECIFICATION.md §6.4 in the TENRYU repository (a public document distributed with the source), and the authoritative defaults are in its §9.1. The default values printed in the per-kernel pages of this site are accurate as of the documentation date in the footer; where the site and SPECIFICATION §9.1 ever disagree, §9.1 wins. Consult the specification when writing a new deck, changing mode, relying on a default, or resolving a validation error.
