Running simulations reference

This page assumes a built build/tenryu and takes you all the way through: complete a first run, write your own deck, and fix things when they break. TENRYU's input is one Python file, called the deck. At initialization, TENRYU evaluates the deck's Python functions into tables and fixes the settings in a JSON (the frozen configuration). This operation is called freezing; afterwards Python never runs inside the time loop. The meanings of freeze, effective value, limiter, and floor are explained in the terms section.

At a glance

  • Four CLI subcommands cover normal use: run (execute), validate (check without running), verify (registered verification cases), and freeze (write the frozen configuration as JSON). Always validate before running; nearly all configuration mistakes are caught before execution.
  • For a first run, execute a template from examples/templates/ as-is; it completes without any editing.
  • tenryu always means the built executable build/tenryu — there is no install step. Invoke it by path from the repository root, or add build/ to PATH.
  • The schema is strict: unknown keys, wrong types, and unsupported combinations stop with an error rather than a warning, and typos get suggestions like did you mean 'kappa_a'?.
  • Re-running into the same output directory does not overwrite; results go to a numbered sibling like _001. If "nothing changed", check the output location first.

Prerequisites

Machine and compiler conditions are on System requirements; producing build/tenryu is covered by Building. Everything below assumes a finished build and a shell at the repository root.

A first run (complete a template)

examples/templates/ ships three runnable skeletons with comments on every block. Start with the lightest one, the radiation slab, unmodified:

# 1. pre-flight check (does not run; takes seconds)
./build/tenryu validate examples/templates/template_1d_slab_radiation.py

# 2. run
./build/tenryu run examples/templates/template_1d_slab_radiation.py

# 3. inspect the results (location set by the deck's Output(directory=...))
ls outputs/template_1d_slab_radiation/results/

If step 3 shows snapshots like <name>_0000.h5 next to <name>_history.h5, the run completed. While the run proceeds, the console (and log/ under the output directory outputs/<name>/) shows step progress and output events like [output] wrote snapshot (step=…, …). The fastest way to look at the data is the bundled tool:

python3 -m tools.tenryu_plot profile outputs/template_1d_slab_radiation   # spatial profiles
python3 -m tools.tenryu_plot history outputs/template_1d_slab_radiation   # time series

Copy a template and rename it before editing. The three Studio presets validated through to their physics metrics are on Examples & presets.

Deck anatomy

A deck calls functions named blocks to write its settings; there are 11 blocks. Main identifies the case and supplies its dimension and stopping conditions. Mesh creates the domain and the division into cells (zoning). Materials registers materials with equation of state (EOS) and opacity models, while Geometry maps initial volume fractions, density, temperature, and velocity onto the mesh. Radiation and Laser select physical operators. Numerics collects the dt, hydrodynamics, conduction, arbitrary Lagrangian–Eulerian (ALE), and safety controls. Output sets file locations and cadence, and Diagnostics chooses quantities accumulated during the run. Parallel sets the domain decomposition for the Message Passing Interface (MPI), and Burn sets nuclear burn.

The following is a minimal complete 1D spherical deck made only from real keys. It fills the domain with one ideal-gas material and advances Lagrangian hydrodynamics with radiation, laser drive, and conduction disabled. Its values demonstrate the input form; they do not define a physics benchmark.

from tenryu_namelist import *

fuel = Material(
    name="fuel", A=2.0, Z=1.0,
    eos=dict(model="ideal_gas", ideal_gas=dict(gamma=5.0 / 3.0)),
    opacity=dict(model="constant", kappa_a=0.0, kappa_s=0.0,
                 units="cm2_per_g"),
)

Main(name="minimal_1d", dimension="1D_SPH", temperature_model="2T",
     t_end=1.0e-9, max_steps=1000, seed=12345)
Mesh(r_min=0.0, r_max=0.05, nr=64, grid="uniform",
     motion="lagrangian")
Materials(materials=[fuel])
Geometry(
    volfrac=dict(fuel=lambda r_cm: 1.0),
    rho=lambda r_cm: 1.0,
    Te=lambda r_cm: 1.0,
    Ti=lambda r_cm: 1.0,
    velocity=None,
    radiation_field="zero",
)
Radiation(enabled=False)
Laser(enabled=False)
Numerics(
    dt=dict(initial_s=1.0e-12, max_s=1.0e-10, min_s=1.0e-18,
            cfl_hydro=0.3),
    hydro=dict(boundary_1d="free"),
    conduction=dict(enabled=False),
)
Output(directory="outputs/minimal_1d", plot_every=10,
       history_every=1, checkpoint_every=100)
Diagnostics(enabled=True, every=1)

Principles for writing your own decks

  • Units are always cgs + eV. Length cm, time s, density g/cm³, temperature eV. To write in µm, define um = 1.0e-4 yourself and convert. Only keys whose names state a unit (wavelength_nm, …) are exceptions.
  • Spatial profiles and time waveforms are functions. At initialization, Geometry.rho/Te/Ti/volfrac are evaluated by passing the cell-center coordinate as a scalar (float), one cell at a time, and laser powers and Marshak temperatures by passing the time as a scalar, one time at a time; all of them are then frozen into tables. A function takes a number and returns a number: NumPy functions may be used, but they must work on scalar arguments. A deck that relies on mutable external state or per-step re-evaluation is incorrect.
  • Unwritten keys take defaults. The canonical defaults are listed in docs/SPECIFICATION.md §9.1. When unsure, leave the key out and confirm effective values in the validate summary and config/*_frozen.json in the output directory.
  • Typos stop the run. Unknown blocks or keys, numbers where strings belong, negative cell counts, and combinations unsupported in the chosen dimension raise a ConfigError instead of being silently ignored. When a "did you mean …?" suggestion appears, apply it.
  • Add physics one piece at a time. Cross-beam energy transfer (CBET), hot electrons, nonlocal conduction by the Schurtz–Nicolaï–Busquet (SNB) model, plasma viscosity, and nuclear burn work only when the deck writes their enabling keys; all are disabled by default (the keys are listed in Dimension and activation at a glance). Bring a new deck up first on a small mesh with a short t_end, then raise the resolution and output cadence to production values.

Terms used in this calculation

Four terms on this page carry a meaning specific to running TENRYU: freeze, effective value, limiter, and floor. The deck, blocks, and keys are defined on the namelist page.

Freeze

Freezing is the operation that fixes the contents of the deck, before the time loop starts, in a form that does not change inside the loop. This page uses the word in two senses.

  • Evaluating functions into tables. The deck's Python functions (callables) are evaluated over the grid and the time axis and replaced by tables of numbers. The spatial functions Geometry.rho, Te, Ti, and volfrac are, by default, evaluated by passing the coordinate of each cell center (the centroid in 2D) as a scalar (float), one cell at a time, and give the initial value of each cell. Geometry.velocity is evaluated at the node coordinates. The time functions (LaserBeam.power; Radiation.boundary.marshak_Tr and its per-face form marshak_Tr_map; Numerics.hydro.boundary_pressure; Laser.hot_electron.eta_hot_table and its per-source form eta_table) are evaluated by passing the time as a scalar, one time at a time, and become piecewise-linear tables. The table times are taken every \(2^{-40}\) s (about \(9.1\times10^{-13}\) s) from 0 to Main.t_end. Where the function's value at the midpoint of an interval differs from the mean of its two end values by more than \(10^{-6}\) times the largest absolute value of the three, the interval is bisected and points are added, down to a spacing of \(2^{-47}\) s. For a run longer than about 0.95 µs, the base spacing is doubled until the number of intervals is at most \(2^{20}\). In the time loop, the table is used by linear interpolation.
  • Fixing the settings in a JSON. When the deck has run, TENRYU checks the keys of every block, fills the keys the deck leaves out with their defaults, and writes the whole configuration as one JSON (the frozen configuration). A function enters the JSON not as values but as its name, its repr (string representation), and the SHA-256 hash of its source code (source_hash). The SHA-256 hash of the deck text (_namelist_source_hash) is also included.

There are two reasons to freeze. First, Python must not be called inside the time loop. TENRYU starts the embedded Python interpreter only to run and freeze the deck, and shuts it down before the time loop starts. A design that calls a Python function at every step would harm speed and reproducibility, so the specification forbids it (docs/SPECIFICATION.md §6.3.1 in the repository). Second, a restart must be checked against the original run: the settings have to be the same.

Freezing affects three things.

  • The frozen-configuration file. tenryu run writes the frozen configuration to config/<name>_frozen.json in the output directory (Output.save_frozen_config, default True), and puts a copy of the deck in config/<name>_namelist.py (Output.save_namelist_copy, default True). The file holds the values with the run-time overrides applied (--output-dir, and --t-end and --max-steps of a restart), plus the freezing time (_frozen_at), the TENRYU version (_tenryu_version), and a summary of the evaluated tables (frozen_summary). The summary holds the minimum, maximum, and mean of the initial density, the minimum and maximum of the electron and ion temperatures, the volume of each material, and the range, number of points, maximum, and integral of each time table. It serves as the primary record of a run's provenance (Outputs & analysis).
  • tenryu freeze. It runs the deck and writes only the frozen configuration. It builds neither the mesh and initial state nor the tables, so frozen_summary is absent and there are no run-time overrides. Give the output file with -o <file>; without it, the file is <deck file name without extension>_frozen.json in the current directory. A copy of the deck is also placed in the same directory as the output file (unless it is already there).
  • The check at restart. A checkpoint stores the frozen configuration in metadata/frozen_config and the deck text in metadata/namelist_source. A restart compares this frozen configuration with the one made from the deck used for the restart, leaving out Main.restart_from (keys that an old checkpoint lacks are filled with defaults before the comparison). If anything differs, the run stops before the time loop starts. A deck that differs by a single character changes _namelist_source_hash, so the restart is refused. The refusal message (checkpoint frozen_config JSON mismatch) lists up to 8 differing keys after differs at: (Checkpoints and restart). The frozen configuration used for the comparison is made from the values before the run-time overrides and holds neither the freezing time, the version, nor the table summary. A checkpoint of a run started with --output-dir or continued with --t-end can therefore be restarted with the unchanged deck.

Effective value

An effective value is the value a run actually uses: the value written in the deck, completed with the defaults of the keys the deck leaves out, with the run-time overrides applied (--output-dir, and --t-end and --max-steps of a restart). It does not mean a root-mean-square (RMS) value. What the deck writes does not show what the run used, because defaults are filled in and overrides are applied; when it is doubtful that a setting took effect, check the effective values first (When it does not work). The effective values a run used are in config/<name>_frozen.json in the output directory. To check them before a run, read the output of tenryu freeze (run-time overrides are not included). The summary of tenryu validate shows the main effective values in a human-readable form. The temperature floors are an example of an effective value that differs from what the deck writes: when the deck does not write a temperature floor (Numerics.floors.Te_floor_eV, Ti_floor_eV) and the lowest temperature of a table EOS is above the default floor of \(10^{-3}\) eV, the floor is raised to that lowest temperature, and the frozen configuration holds the raised value (docs/NUMERICS.md §1.1.5 in the repository).

Limiter

A limiter is the name of the constraint that set the time step \(\Delta t\) of a step. \(\Delta t\) equals the smallest of the caps proposed by the physics kernels, the growth limit, Numerics.dt.max_s, landing on the output time, and the remaining time, and the name of the winning candidate (hydro, conduction, braginskii, burn, hot_electron, growth, max, output, t_end, …) is the limiter. With Main.verbosity="verbose", it appears at every step as dt_winner= in the [dt_breakdown] line of the log, and it is also kept in the history as dt_winner. When \(\Delta t\) keeps shrinking, the limiter points to the kernel that causes it (What you see while it runs). The list of names and the decision rule are on Time-step control & CFL. The flux-limiting function of flux-limited diffusion (the flux limiter) and the slope limit of the ALE remap (remap_limiter) are different things.

Floor

A floor is a lower bound on density and temperature. When a value falls below its bound during the calculation, it is raised to the bound (a clamp), and the energy this takes is booked in the energy ledger. A floor is not a physical model but a numerical safety device that keeps NaNs and negative temperatures from breaking the calculation, and every activation is counted (Floors, clamps, and safety guards). The keys are rho_floor_gcc (default \(10^{-10}\) g/cm³) and Te_floor_eV and Ti_floor_eV (default \(10^{-3}\) eV) of Numerics.floors; Studio writes the same values. A floor is distinct from the lower bound on the time step, Numerics.dt.min_s: when \(\Delta t\) falls below this bound, the run stops with a FATAL error (the default when the deck does not specify it is \(10^{-20}\) s; Studio writes \(10^{-22}\) s).

What you see while it runs

run first checks the deck's input (the same checks as validate), freezes it, builds the mesh and initial state, and enters the time loop. From there the log carries step progress, and every snapshot or checkpoint write emits a line such as [output] wrote snapshot (step=…, …) or [output] wrote checkpoint (step=…, …). Logs go both to the console and to outputs/<name>/log/.

When "\(\Delta t\) keeps shrinking and the run crawls", read the limiter name in the log (hydro, conduction, braginskii, …) to identify the limiting kernel, then revisit that physics (floors, zoning). The decision rule and every kernel's formula are collected on Time-step control & CFL.

Output locations

Snapshots, history, and checkpoints go under Output.directory; outputs/<name> is the standard organization. The directory contents (results/, config/, checkpoints/, log/, run_info.json), file naming, and the dataset lists are on Outputs & analysis. plot_every, history_every, and checkpoint_every are step-count cadences (0 disables); the _s variants (plot_every_s, …) are seconds-based, and both fire under OR logic. To specify cadence in time, always use the _s keys; confusing step counts with seconds is a common unit mistake.

Checkpoints and restart

A restart runs the original deck file, unchanged, and passes the checkpoint prefix (without any rank suffix or .h5) with --restart — e.g. ./build/tenryu run minimal_1d.py --restart outputs/minimal_1d/checkpoints/minimal_1d_ckpt_0000. A restart compares the checkpoint's frozen configuration with the one made from the deck used for the restart, covering the hash of the deck text and every setting except Main.restart_from (freezing); if they do not match, the run fails before starting (checkpoint frozen_config JSON mismatch). Any edit of the deck — adding restart_from, a longer t_end, another output interval, even a comment — prevents the restart. To keep the prefix in the deck, have the deck of the original run read it from the environment, e.g. restart_from=os.environ.get("RESTART_FROM", ""), so the text does not change. A prefix that matches no checkpoint also fails before starting. The restart inherits the stored state, time, time step, and next output times. It writes to the deck's Output.directory, or to a new directory numbered _001, _002, … when that one exists. A 1D run restarted from an intermediate checkpoint written on or after 2026-09-26 continues bitwise identical to the original run. Every history column was checked to match with the GXII (GEKKO XII) FLD and discrete-ordinates (SN) decks and with a deck that includes nuclear burn. Runs that reuse the previous ray tracing, rescaled by the power ratio (Laser.raytrace_skip_config.enabled=True, default False), retrace every ray right after the restart and therefore do not match. To restart a 1D SN run from before 2026-09-25, set Radiation.sn_transport.spatial_scheme="linear_characteristic" to continue with the former spatial scheme.

Continuing a run

To continue a finished run to a later end time or step limit, keep the deck unchanged and pass the new value on the command line: ./build/tenryu run <deck.py> --restart <checkpoint> --t-end <s> (or --max-steps <N>). To continue from the end of a run, give the original deck Output(..., write_final_checkpoint=True) so that a checkpoint of the final step is kept. The same works from an intermediate checkpoint, and a run continued from a checkpoint before the deck's t_end is bitwise identical to a run started with the longer value in the deck (checked in 1D with FLD). The new value does not enter the checkpoint's frozen configuration (it keeps the deck's), so a continued run's checkpoints can be continued again with the same deck and another value; the values in effect are recorded as t_end and max_steps in run_info.json. --t-end and --max-steps apply to restarts only; a restart from a checkpoint that is already at the end time or step limit without them stops before starting and names the option to pass. LaserBeam.energy_J keeps normalizing the power over the deck's t_end; a pulse that goes on after it delivers extra energy in the extended interval (the amount is reported in a WARNING). A continued run writes next to the deck's Output.directory, in _001 and so on. When it continues from an intermediate checkpoint it recomputes the end of the earlier output, and Studio's history chart and TENRYU Scope (the snapshot list and the time-space diagram) show that interval from the continuation.

When it does not work

An input error is reported as a ConfigError or ValueError exception (Validation and defaults); it is printed on a line that begins with TENRYU ERROR [namelist]:, and the command stops with exit status 1. An error found while the deck executes follows Python execution failed: RuntimeError: with the cause, and the line after At: shows the deck line. Any other exception raised while the output is prepared or inside the time loop is printed with TENRYU ERROR [run]:. A failed assertion prints a line that begins with TENRYU_ASSERT failed:, followed by the condition and the cause, and the process aborts.
