TENRYU Studio (GUI) reference

TENRYU Studio is a desktop application for creating TENRYU Python namelist decks through a form. It generates the deck live as inputs change and brings validation, saving, and local or server execution into one workspace. A saved deck also carries its form state, so a configuration can move between code and the GUI without a separate project file.

At a glance

  • Editing the center form immediately updates the Python deck in the right pane.
  • Pass both form validation and server-side tenryu validate before saving or running.
  • Keep the TENRYU-GUI-STATE comment to restore the complete form from a saved deck.
  • Three physics presets were run to completion on an RTX 4090 on 2026-07-31.

Obtaining and launching

Studio ships inside the repository's gui/ directory (there is no standalone distribution). The core of Studio is a pure web application: for a development launch, run npm install in gui/, then run npm run bridge (the local execution bridge) and npm run dev (the Vite dev server, http://localhost:5173) side by side and open it in a browser. The Mac native app (the Tauri shell) can be built only on a Mac. See gui/README.md in the repository for the detailed procedure.

From form to run

Studio's left navigation follows the normal setup order: Presets, Basic settings, Materials, Geometry, Physics, Drive, and Output. The center pane contains the selected form, while the live deck in the right pane always shows the latest Python namelist. Missing required values or inconsistent combinations produce errors in place; deck generation resumes after they are corrected. The live deck makes the TENRYU cgs + eV contract visible while editing: lengths are in cm, times in s, temperatures in eV, and densities in g/cm³.

The basic sequence is form → live deck → validate → save or run. A preset is a starting point, and every field remains editable after it is applied. Read the generated deck, resolve all validation errors, then save it to a file. The result is an ordinary Python deck: it can be run outside Studio with ./build/tenryu run deck.py and inspected in any text editor.

Round-tripping with TENRYU-GUI-STATE

Studio embeds a TENRYU-GUI-STATE comment near the beginning of every deck it saves. Opening that deck restores the entire form—including materials, regions, physics, drive waveforms, and output settings—and restarts live generation. The executable deck itself is therefore the unit to share or archive; there is no separate GUI project file to keep synchronized.

To import hand-edited Python after saving, delete the TENRYU-GUI-STATE comment; while the comment remains, the form state stored in it takes precedence. Both loading a file and pasting text let you set, before the Python is evaluated, the working directory, the environment variables (KEY=VALUE per line), and the evaluation venue (local python3 or the selected server).

Set the working directory to the directory from which you run the deck. Navigate the server's directories with “Browse…” beside the directory field and confirm with “Select this folder” in the picker. The server default is the temporary upload directory; if evaluation fails with this default, Studio asks you to select the directory from which the deck is run. When a file is loaded with the working directory left blank, Studio tries candidate directories in turn and adopts the first in which evaluation succeeds: locally, the deck's directory and its ancestors; on a server, the directories of same-named copies of the deck found there and their ancestors. When the file is opened with ⌘O, Studio makes this attempt before showing the dialog and, on failure, lists the directories tried.

Studio detects environment-variable reads that name the variable with a string literal, lists them, and appends missing NAME= lines when the source changes. Empty values are not sent, so inherited environment variables and deck defaults still apply. The import settings remain available for the session and are recorded in the import report and in the header of the saved deck. After a successful file import, Studio saves the venue, working directory, and environment text by file path in the app settings (up to the 50 most recent paths) and restores them ahead of the venue default when the same file is imported again. Environment values are stored as plain text in the header and the app settings.

Import evaluates the source and its callables several times in child processes (45-second timeout each). On a server, Studio uploads the import scripts bundled with the app, the request JSON, and the deck to a temporary directory under the profile's run directory and removes them afterwards; files the deck depends on must exist on that server. Only import trusted code.

The import report lists values mapped to the form, functions verified at sample points, settings preserved from the source Python, and omitted defaults. Mapped form values are fixed at import time; source-preserved settings follow the working directory and environment in effect when the solver runs. The helper embedded in the saved deck that replays the source Python at initialization (deck_import_runtime.py) changes neither the working directory nor the environment, and the environment variables entered for the import are not applied to solver runs. A form edit that conflicts with a source-preserved setting is rejected. A plain local deck needs no server or mirror, but a deck that imports tools.mesh_planner may need the TENRYU repository: locally, a checkout or the assistant's copy synced from the server's checkout (the mirror); on a server, that server's checkout. Fill in the optional “Source filename on the venue” field when the deck depends on __file__ or on modules beside the source file. When you move a saved deck, move the data and modules it requires with it.

Run-validated 1D presets

In addition to a blank setup, the 1D tab under Presets provides three physics presets. These were not merely accepted by the schema: each was run to its endpoint on an RTX 4090 on 2026-07-31 and checked for its characteristic physical result.

  • Radiation slab: a 120 eV Marshak drive and grey FLD produce a heat front near 35 µm at 1 ns, with a cold region still ahead of it.
  • Laser implosion capsule: a GXII-class 10 TW × 1 ns drive (GXII: the GEKKO XII laser — see the linked benchmark definition), DT + CH target, corona ramp, and 20-group FLD gave about 86% absorption and maximum compression near 1.4 ns when the preset was validated on 2026-07-31. This preset's ≈86% is not comparable with the regression deck's ≈93% or the ≈45% of the cross-code benchmark against HELIOS — the Examples page lists the three conditions.
  • Indirect-drive Tr(t): with a Marshak waveform rising from a 120 eV foot to 200 eV, the run follows stagnation at 4.2–4.5 ns and the subsequent rebound.

The Examples & presets page records the numerical inputs and measured values. When modifying a case, first retain an unmodified short reference run, then vary one input at a time, so that changes in absorption, compression, and output cadence become easier to identify.

Validate and run on a server

Define an execution profile and TENRYU binary in the “Servers” view, then select that profile in the header. “Run validate” in the validation panel sends a temporary deck to the selected server and performs dry-run validation there. “Run ▶” submits the validated setup to the same server. The “Run history” view keeps each run's status (queued, running, completed, or failed) and provides access to its results. Without a configured server, deck generation and saving still work; run the saved file with the TENRYU command line on a suitable host.
