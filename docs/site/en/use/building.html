Building reference

TENRYU configures its C++20 and CUDA C++ sources with CMake and Ninja. The supported build target is an NVIDIA GPU (default fatbin: sm_70/80/89/90; continuously exercised hardware is sm_80 or newer) with a CUDA 12.x toolkit. This page covers a Release build, three levels of testing, the MPI option, and ccache for faster rebuilds.

At a glance

  • Install a CUDA 12.x toolkit, CMake 3.25 or newer, Ninja, and use an NVIDIA GPU (exercised hardware is sm_80+).
  • The standard workflow configures build/ with cmake, then compiles it with ninja -C build.
  • Use the complete CTest suite, a targeted -R selection, or a named tenryu verify case according to the scope of the check.
  • MPI is OFF by default. Configure with -DTENRYU_ENABLE_MPI=ON for a multi-rank executable.

Prerequisites

Build on a system where the NVIDIA driver and CUDA compiler are available and CMake can discover the selected dependencies. HDF5 and Python support are enabled by default in the top-level CMake configuration; MPI is disabled by default. Any optional feature also requires its development package to be visible during configuration. The complete requirement picture — supported GPU generations, compilers, minimum library versions, CMake option defaults, and pre-flight check commands — is on System requirements; the table below restates the essentials.

About networking. The small test/logging/CLI dependencies (Catch2, spdlog, CLI11, pybind11) are fetched automatically by CMake's FetchContent at configure time when missing. On offline machines, preinstall them or run the first configure where the network is available. CUDA, HDF5, Python, MPI, and Hypre are never auto-fetched.

Getting the source

The source code is hosted on GitHub at tenryu-code/TENRYU. Every step below runs from the root of the cloned repository.

git clone https://github.com/tenryu-code/TENRYU.git
cd TENRYU

To use a specific release, check out its tag (for example git checkout v1.0.0-beta.1). To update an existing checkout, run git pull and rebuild.

Configure and build

Run these commands from the repository root. The first leaves the source tree untouched and creates a Release build tree in build/. The second compiles the default targets, producing build/tenryu and the enabled test targets.

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
ninja -C build

After changing sources, an incremental ninja -C build is normally sufficient. When changing a CMake option, rerun the configure command with the new option before invoking Ninja. If configuration reports a missing dependency, install that package and repeat the same configure command.

Once the build succeeds, run one registered analytic case as the minimal end-to-end smoke check, time loop included:

./build/tenryu --help          # the CLI starts
./build/tenryu verify noh      # an analytic case PASSes (uses the GPU)

With these passing, continue to the template walkthrough on Running simulations.

Three test tiers

The three entry points answer different questions. The complete CTest run checks the configured build broadly. A targeted CTest gives a short loop around a changed module. A named verification runs one analytic problem, benchmark, or regression directly. The complete CTest run keeps failure output visible.

ctest --test-dir build -j8 --output-on-failure
ctest --test-dir build -R <pattern>
./build/tenryu verify <name>
TierWhen to use itSelection
Complete CTestBefore integration or after a broad change.Runs every test registered in the build tree, with eight-way parallelism.
Targeted CTestFast iteration during development.Replace <pattern> with a test-name regular expression, such as a module or verification name.
Named verifyOne analytic case, benchmark, or golden regression.Replace <name> with a registered name such as sedov or gxii_1d_fld_regression.

Because -R performs regular-expression matching, it can select more tests than an exact name would. Inspect the CTest listing (ctest --test-dir build -N -R <pattern>) first when the boundary matters. Also distinguish skips from passes in the log: a test that did not run because a GPU or optional dependency was unavailable is not evidence that the tested behavior passed.

MPI build

Add the MPI option to the same Release configuration for multi-rank runs. Execute it where CMake can find an MPI implementation and its headers.

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DTENRYU_ENABLE_MPI=ON
ninja -C build

TENRYU_ENABLE_MPI is a top-level CMake option whose default is OFF. If an existing build/ tree is reconfigured with the option changed, run Ninja afterward so it can rebuild the affected targets. See the MPI decomposition page for launch syntax and rank-to-GPU placement.

Faster rebuilds with ccache

For repeated compilation, especially after header changes, make ccache the compiler launcher. With ccache available on PATH, append both settings to the configure command:

-DCMAKE_CXX_COMPILER_LAUNCHER=ccache \
-DCMAKE_CUDA_COMPILER_LAUNCHER=ccache

Set both launchers so C++ and CUDA compilation can use the cache. ccache accelerates matching compilation work; it does not replace configuration, linking, or testing. A changed toolchain, compile option, or included header changes the cache key and causes the necessary compilation to run normally.
