シミュレーションの実行 reference

このページは、ビルド済みの build/tenryu を前提に、「最初の 1 本を完走させる → 自分のデッキを書く → つまずいたら直す」までを通しで説明する。TENRYU の入力は 1 個の Python ファイル（namelist デッキ）である。Python の関数は初期化時に評価して表へ凍結されるため、時間ループの最中に Python が呼ばれることはない。

要点

  • CLI は 4 つ: run（実行）・validate（実行せず検査）・verify（登録済み検証ケース）・freeze（凍結 JSON の出力）。run の前に必ず validate — 設定ミスは実行前にほぼ全部見つかる。
  • 最初の 1 本は examples/templates/ のテンプレートをそのまま実行すればよい。写経なしで完走する。
  • tenryu とは常にビルドされた実行ファイル build/tenryu のことである — インストール手順はない。リポジトリのルートからパス指定で起動するか、build/ を PATH に加える。
  • スキーマは厳格である。未知のキー・型違い・不正な組合せは警告ではなくエラーで止まり、打ち間違いには did you mean 'kappa_a'? のような修正候補が出る。
  • 同じ出力先へ再実行すると上書きせず _001 の連番ディレクトリへ書かれる。「結果が変わらない」と思ったらまず出力先を確認する。

前提

マシン・コンパイラの条件は動作環境と要求スペック、build/tenryu の作り方はビルドを参照のこと。以下はビルドが済んでいて、リポジトリのルートにいる前提で書く。

CLI サブコマンド

コマンド入力用途
tenryu validate <deck.py>任意のデッキ実行せずに検査する（数秒）。スキーマ・組合せの検査に加え、次元・格子・材料・物理モジュールの ON/OFF・出力先をまとめた実行前サマリを表示する。要約を目で確認してから run — これが最も安上がりなデバッグである。
tenryu run <deck.py>任意のデッキ本実行。デッキを読み、検証・凍結し、メッシュ・材料表・初期条件を作ってから時間ループに入る。--output-dir <dir> でデッキを編集せずに出力先を上書きできる（新規 run 専用。restart との併用は ConfigError）。
tenryu verify <name>登録済みケース名解析解・基準解・統合検査の再実行（例: sedov、noh、gxii_1d_fld_regression）。検証とベンチマーク参照。
tenryu freeze <deck.py>任意のデッキ凍結後の設定 JSON を書き出す。実行せずに「実効値」を確認・差分比較したいときに使う。

最初の 1 本（テンプレートを完走させる）

examples/templates/ に、全ブロックへコメントを付けた実行可能な雛形が 3 本ある。まずは一番軽い輻射スラブをそのまま動かす。

# ① 実行前検査（実行しない。数秒で終わる）
./build/tenryu validate examples/templates/template_1d_slab_radiation.py

# ② 実行
./build/tenryu run examples/templates/template_1d_slab_radiation.py

# ③ 結果の確認（出力先はデッキの Output(directory=...) が決める）
ls outputs/template_1d_slab_radiation/results/

③ で <name>_0000.h5 のようなスナップショットと <name>_history.h5 が並んでいれば完走である。実行中はコンソール（と、出力先 outputs/<name>/ 配下の log/）にステップの進行と、[output] wrote snapshot (step=…, …) のような出力イベントの行が流れる。最短の可視化は付属ツールで足りる:

python3 -m tools.tenryu_plot profile outputs/template_1d_slab_radiation   # 空間プロファイル
python3 -m tools.tenryu_plot history outputs/template_1d_slab_radiation   # 時系列
テンプレート内容学べること
template_1d_slab_radiation.py平面 1D・灰色 FLD・Marshak 境界駆動・流体 OFF放射伝播の最小構成。validate → run → 可視化の流れ。
template_1d_laser_sphere.py球 1D・レーザー直接照射・2 温度・伝導 ONレーザー波形の書き方、複合物理。
template_1d_indirect_tr.py球 1D・Tr(t) 間接照射駆動時間依存 callable → 凍結テーブルの流儀。

改造の定番は、駆動温度・レーザーパワー（callable の返り値）を変える、nr を倍にして収束を見る、Radiation(mode="sn_transport") にして FLD と比べる、の 3 つである。テンプレートはコピーして名前を変えてから改造する。物理指標まで確認済みの Studio プリセット 3 種は例題とプリセットにある。

デッキの構造

Main はケース名、次元、終了条件を定め、Mesh は計算領域とゾーニングを作る。Materials には EOS と不透明度をもつ材料を登録し、Geometry の関数が初期の体積分率、密度、温度、速度を空間へ割り当てる。Radiation と Laser は演算子を選び、Numerics は時間刻み、流体、熱伝導、ALE と安全のための制御をまとめる。Output はファイルの場所と出力の間隔を、Diagnostics は実行中に集計する量を決める。

次は、実在するキーだけで構成した最小の 1 次元球対称のデッキである。単一の理想気体の材料で一様に満たし、輻射・レーザー・熱伝導を無効にしてラグランジュ流体を進める。値は入力形式を説明するためのものであり、物理的なベンチマークではない。

from tenryu_namelist import *

fuel = Material(
    name="fuel", A=2.0, Z=1.0,
    eos=dict(model="ideal_gas", ideal_gas=dict(gamma=5.0 / 3.0)),
    opacity=dict(model="constant", kappa_a=0.0, kappa_s=0.0,
                 units="cm2_per_g"),
)

Main(name="minimal_1d", dimension="1D_SPH", temperature_model="2T",
     t_end=1.0e-9, max_steps=1000, seed=12345)
Mesh(r_min=0.0, r_max=0.05, nr=64, grid="uniform",
     motion="lagrangian")
Materials(materials=[fuel])
Geometry(
    volfrac=dict(fuel=lambda r_cm: 1.0),
    rho=lambda r_cm: 1.0,
    Te=lambda r_cm: 1.0,
    Ti=lambda r_cm: 1.0,
    velocity=None,
    radiation_field="zero",
)
Radiation(enabled=False)
Laser(enabled=False)
Numerics(
    dt=dict(initial_s=1.0e-12, max_s=1.0e-10, min_s=1.0e-18,
            cfl_hydro=0.3),
    hydro=dict(boundary_1d="free"),
    conduction=dict(enabled=False),
)
Output(directory="outputs/minimal_1d", plot_every=10,
       history_every=1, checkpoint_every=100)
Diagnostics(enabled=True, every=1)

自分のデッキを書くときの原則

  • 単位は常に cgs + eV。長さ cm・時間 s・密度 g/cm³・温度 eV。µm で書きたいときは um = 1.0e-4 を自分で定義して換算する。名前が単位を明示するキー（wavelength_nm など）だけが例外である。
  • 空間分布と時間波形は関数で与える。Geometry.rho・Te・Ti・volfrac はセル中心座標に対して、レーザーパワーや Marshak 温度は時間に対して、初期化時に一度だけベクトル化評価され、凍結された表へ変換される。関数が外部状態を持ち続けることや、実行中に再評価されることを前提にしたデッキは正しくない。
  • 書かなかったキーは既定値になる。既定値の正典はリポジトリの docs/SPECIFICATION.md §9.1。迷ったら書かず、validate の要約と出力先の config/*_frozen.json で実効値を確認するのが安全である。
  • 打ち間違いはエラーで止まる。未知のブロックやキー、文字列を要求する場所への数値、負のセル数、選んだ次元では対応していない組合せは、黙って無視されず ConfigError になる。修正候補（did you mean …?）が出たらそのまま直す。
  • 物理は 1 個ずつ足す。opt-in 群（CBET・ホット電子・SNB・粘性・燃焼など）は「書かなければ完全に不活性」という契約で実装されている。新しいデッキは、まず小さいメッシュと短い t_end で初期化と数ステップを確認し、そのあとで実運用の解像度と出力の間隔へ上げること。

実行中に見えるもの

run は最初にデッキを検証・凍結し（validate と同じ検査）、メッシュと初期状態を構築してから時間ループへ入る。以後はステップの進行がログに流れ、スナップショット・チェックポイントを書くたびに [output] wrote snapshot (step=…, …) の行が出る。ログはコンソールと outputs/<name>/log/ の双方に残る。

「\(\Delta t\) がどんどん小さくなって進まない」ときは、ログの limiter 名（hydro・conduction・braginskii など）で律速カーネルを特定し、該当物理の設定（床値・格子）を見直す。決定則と全カーネルの式は時間刻み制御と CFL にまとめてある。

出力先

実行時の描画、履歴、チェックポイントは Output.directory に書き出される。ケース名に合わせた outputs/<name> が標準的な整理の仕方である。ディレクトリの内訳（results/・config/・checkpoints/・log/・run_info.json）、ファイルの命名、全データセットの一覧は出力と解析にまとめた。plot_every・history_every・checkpoint_every はステップ数で指定する間隔（0 で無効）、_s 付き（plot_every_s 等）は秒で指定する間隔で、両方が有効なら OR で発火する。時間で指定したいときは必ず _s 付きを使う — 単位事故の定番ポイントである。

チェックポイントと再開

再開するデッキでは、Main.restart_from にチェックポイントの接頭辞を指定する。たとえば Main(..., restart_from="outputs/minimal_1d/checkpoints/minimal_1d_ckpt_0100") のように、ランクの接尾辞や .h5 を除いた接頭辞を渡す。再開は、チェックポイントに保存された状態、時刻、時間刻みを引き継ぎ、元の出力の配置をそのまま続ける。指定した接頭辞に一致するチェックポイントがない場合や、凍結後の設定と整合しない場合（次元・メッシュ・材料・群・seed の不一致）は、開始する前に失敗する。

うまくいかないとき

症状原因と対処
ConfigError: ... is not a supported key (did you mean 'X'?)キー名の打ち間違い。候補が出るのでそのまま直す。
ConfigError: eos.file is required for model=sesameテーブル EOS はファイル必須。入門は ideal_gas にする。
Radiation.mode="imc_ddmc" でエラー旧 Monte Carlo 輸送は退役済み。書かない（= FLD 既定）か sn_transport にする。imc=dict(...)/ddmc=dict(...) も同様に退役経路専用の互換キーである。
実行したのに結果が古いまま出力先の衝突で _001 の連番ディレクトリへ書かれている。出力先を確認する。
温度が上がらない / 波が進まないまず validate の要約で有効な物理モジュールを確認し、次に config/*_frozen.json で境界・不透明度の実効値を確認する。
\(\Delta t\) が縮み続けて進まないログの limiter 名で律速カーネルを特定する（時間刻み制御）。床（dt.min_s）を割ると FATAL 停止する。
