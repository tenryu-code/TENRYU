TENRYU Studio (GUI) reference

TENRYU Studio は、TENRYU の Python namelist のデッキをフォームから作成するデスクトップアプリである。入力に応じてデッキをその場で生成し、検証、保存、ローカルまたはサーバーでの実行までを、ひとつの画面で扱える。保存したデッキにはフォームの状態も埋め込まれるため、コードと GUI のあいだを行き来しながら設定を育てられる。

GUI マニュアルは gui/manual/ に同梱される別の文書一式で、本サイトにも含まれている。上のボタン（およびトップバーの「GUI マニュアル」リンク）から開ける。

要点

  • 中央のフォームを編集すると、右のペインにある Python のデッキがその場で更新される。
  • フォームの検証と、サーバー上での tenryu validate を通してから、保存または実行へ進む。
  • TENRYU-GUI-STATE のコメントを残しておけば、保存済みのデッキからフォーム全体を復元できる。
  • 3 つの物理プリセットは、2026-07-31 に RTX 4090 上で完走を確認した 1 次元の構成である。

入手と起動

Studio はリポジトリの gui/ ディレクトリに含まれる（単体配布はしていない）。Studio の中核部分は純粋な Web アプリであり、開発起動は gui/ で npm install を済ませたうえで、npm run bridge（ローカル実行ブリッジ）と npm run dev（Vite 開発サーバ、http://localhost:5173）を並走させてブラウザから開く。Mac ネイティブアプリ（Tauri シェル）のビルドは Mac 上でのみ行える。手順の詳細はリポジトリの gui/README.md を参照のこと。

フォームから実行まで

Studio の左のナビゲーションは、プリセット、基本設定、材料、ジオメトリー、物理、駆動、出力を、設定する順に並べている。中央で選択中のフォームを編集すると、右のペインに常に最新の Python namelist が表示される。必須の値が欠けていたり、整合しない組合せがあったりする場合は、その場でエラーを示し、修正すると生成を再開する。右のペインのデッキを見れば、長さは cm、時間は s、温度は eV、密度は g/cm³ という TENRYU の cgs + eV の規約を確認しながら入力できる。

基本の流れは「フォームを作る → 生成されたデッキを読む → 検証する → 保存または実行」である。プリセットは出発点であり、適用したあとの項目はすべて編集できる。右のペインで生成内容を確認し、検証結果のエラーを解消してからファイルへ保存すること。保存したデッキは通常の Python のファイルなので、Studio を介さずに ./build/tenryu run deck.py で実行することも、テキストエディタで内容を確認することもできる。

TENRYU-GUI-STATE による行き来しながらの編集

Studio が保存するデッキの先頭には、フォームの完全な状態を表す TENRYU-GUI-STATE のコメントが埋め込まれる。「読込」でそのデッキを開くと、材料、領域、物理、駆動の波形、出力の設定などが元のフォームへ復元され、デッキの生成が再開される。したがって、配布や保管の単位は実行できるデッキそのものであり、別の GUI 用プロジェクトファイルを同期する必要はない。

保存後に手で編集した Python を取り込むには、TENRYU-GUI-STATE のコメントを削除する。コメントが残っている場合は、コメントに保存したフォームの状態を優先する。ファイルの読込と貼付けのどちらでも、Python を評価する前に、作業ディレクトリ、環境変数（1 行に KEY=VALUE）、評価の実行先（ローカルの python3 または選択中のサーバー）を指定できる。

作業ディレクトリには、そのデッキを実行するディレクトリを指定する。「参照…」でサーバー上のディレクトリを移動し、「このフォルダーを選択」で設定する。サーバーでの既定は一時的な転送先であり、既定のまま評価に失敗すると、実行するディレクトリを選ぶよう案内を表示する。作業ディレクトリを空欄のままファイルを読み込むと、Studio は候補のディレクトリを順に試し、最初に評価に成功したものを採用する。候補は、ローカルではデッキのあるディレクトリとその上位のディレクトリ、サーバーではサーバー上で見つけた同名のデッキのディレクトリとその上位のディレクトリである。⌘O で開く場合は、設定画面を表示する前にこの試行を行い、失敗すると試したディレクトリを表示する。

Studio は、デッキが文字列で名前を指定して読む環境変数を検出して一覧に示し、ソースが変わったときも、欠けている NAME= の行を追加する。値が空の行は送らないため、実行先から継承した環境変数やデッキの既定値がそのまま使われる。取込に使った設定はセッション中も保持され、取込レポートと保存したデッキのヘッダに記録される。ファイルの取込に成功すると、実行先・作業ディレクトリ・環境変数の欄を、ファイルのパスごとに直近の 50 件までアプリ設定へ保存し、次に同じファイルを取り込むときは実行先の既定より優先して復元する。環境変数の値は、ヘッダとアプリ設定に平文で保存される。

取込では、ソースとその中の関数を子プロセスで複数回評価する（各回 45 秒でタイムアウト）。サーバーでは、アプリに同梱した取込用のスクリプト、要求の JSON、デッキを、プロファイルの実行ディレクトリの下の一時ディレクトリへ転送し、終了後に削除する。デッキが依存するファイルは、そのサーバーに置いておく必要がある。信頼できるコードだけを取り込むこと。

取込レポートは、フォームへ対応付けた値、標本点で検証した関数、元の Python のまま保持する設定、追加しない既定値を示す。フォームの値は取込の時点で固定され、元の Python のまま保持する設定は、ソルバを実行するときの作業ディレクトリと環境変数に従う。保存したデッキに埋め込まれ、初期化時に元の Python を再実行するヘルパー（deck_import_runtime.py）は作業ディレクトリも環境変数も変えず、取込時に指定した環境変数もソルバの実行には適用されない。元の Python のまま保持する設定と衝突するフォームの編集はエラーになる。通常のローカルのデッキはサーバーもミラーも必要としないが、tools.mesh_planner を import するデッキは、TENRYU のリポジトリを必要とする場合がある。ローカルでは TENRYU の checkout か、サーバーの checkout から同期したアシスタント用の写し（ミラー）を、サーバーではそのサーバーの checkout を使う。デッキが __file__ や元のファイルの近くのモジュールに依存する場合は、任意の「実行先での元ファイルパス」の欄を指定する。保存したデッキを移動するときは、参照するデータやモジュールも一緒に移すこと。

実行まで確認済みの 1D プリセット

空の構成に加えて、「プリセット」の 1D タブには次の 3 つの物理プリセットを収録している。いずれも単に検証を通しただけの例ではなく、2026-07-31 に RTX 4090 で終端まで実際に計算し、特徴的な物理解が得られることを確認した構成である。

  • 輻射スラブ: 120 eV の Marshak 駆動とグレイ FLD により、1 ns で約 35 µm まで進む熱波の前線と、その前方の低温領域を再現する。
  • レーザー爆縮カプセル: GXII 級（GXII = 激光 XII 号 — リンク先のベンチマーク定義参照）の 10 TW × 1 ns、DT + CH + コロナ層、20 群 FLD により、約 86% の吸収と、約 1.4 ns での最大圧縮が得られた（プリセットを検証した 2026-07-31 の値）。このプリセットの約 86% は、回帰デッキの約 93% や HELIOS とのコード間ベンチマークの約 45% とは比較できない — 3 つの条件の対照は「例題とプリセット」ページにある。
  • 間接照射 Tr(t): 120 eV のフットから 200 eV へ立ち上げる Marshak の波形で、4.2–4.5 ns の停滞と、その後の反跳まで追跡する。

プリセットの数値条件と観測値は「例題とプリセット」のページにまとめてある。条件を変えるときは、まず変更していないプリセットを基準となる短い実行として保存し、そのあとで入力をひとつずつ変えていくと、吸収、圧縮、出力の間隔の差を追いやすくなる。

サーバーで検証・実行する

「サーバー」で実行先のプロファイルと TENRYU のバイナリを設定し、ヘッダーで対象を選ぶ。検証パネルの「validate 実行」は、選んだサーバーへ一時的なデッキを送り、実行せずに検証だけを行う。「実行 ▶」は検証済みの設定を同じサーバーへ投入し、「実行履歴」には待機中、実行中、完了・失敗といった状態と、結果への導線が残る。サーバーを設定しない場合でも、デッキの生成と保存は利用でき、保存先で TENRYU のコマンドラインから実行できる。
